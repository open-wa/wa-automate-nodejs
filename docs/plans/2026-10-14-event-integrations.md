# OpenWA event contracts and MCP Events

Research date: 2026-10-14. This note records the initial source research and the subsequently authorized mini epic. The implementation uses one public event catalog: AsyncAPI describes OpenWA's event interfaces, Fumadocs renders that contract, and MCP Events adds subscriptions that can trigger ChatGPT work. Runtime acceptance remains unperformed; source and documentation generators were run to produce the requested artifacts.

## Verified external requirements

**ChatGPT MCP Events.** OpenAI requires MCP 2.0 revision `2026-07-28`, `server/discover` advertising `events`, and `events/list`, `events/subscribe`, and `events/unsubscribe` on the authenticated tools endpoint. ChatGPT's integration uses outbound webhooks, not SSE or polling. It is available in Work web chats, desktop Work chats with Cloud selected, and dots. Subscriptions need persistent owner/filter/destination/secret/expiry storage, idempotent identity, callback verification, Standard Webhooks signatures, and connection-time public HTTPS address validation with redirects blocked. Send one event per request, at most 256 KiB; preserve its ID across bounded transient retries and stop retrying `410`/`413`. No replay is represented by `cursor: null`. These requirements make this a new subscriber delivery adapter, rather than advertising existing OpenWA webhook support as MCP Events. [Official OpenAI documentation](https://developers.openai.com/plugins/build/mcp-events).

**AsyncAPI.** The currently published specification is 3.1.0; 3.0.0 remains documented. AsyncAPI describes message-driven operations independently of transport, with channels, messages, schemas, bindings, and application-perspective `send`/`receive` operations. An OpenWA server document should describe its actual sends, not reverse a receiver's contract mechanically. [3.1 specification](https://www.asyncapi.com/docs/reference/specification/v3.1.0), [3.0 specification](https://www.asyncapi.com/docs/reference/specification/v3.0.0).

**Parser support.** Published `@asyncapi/parser` is 3.6.4, depending on `@asyncapi/specs ^6.11.1`; its supported versions come from that dependency's schema keys. The published parser browser artifact contains schemas for both 3.0.0 and 3.1.0. Therefore 3.1 is not blocked by current parser support. This is source inspection, not evidence that OpenWA's future document validates. [Published parser metadata](https://registry.npmjs.org/@asyncapi%2fparser/3.6.4), [version selection source](https://github.com/asyncapi/parser-js/blob/1ba9a5bb26d01082d2e829bf6645793d13428b3b/packages/parser/src/constants.ts), [published parser artifact](https://registry.npmjs.org/@asyncapi/parser/-/parser-3.6.4.tgz).

## Fumadocs compatibility and smallest integration

The latest published `@fumadocs/asyncapi` is **0.4.4**. Its peer ranges are `fumadocs-core ^16.15.0`, `fumadocs-ui ^16.15.0`, and React/React DOM `^19.2.0`. OpenWA currently has core/UI **16.15.15**, MDX **15.4.5**, and React/React DOM **19.3.0**, so the declared peer ranges admit the current stack without a framework upgrade. This establishes declared compatibility, not a successful TanStack/Cloudflare build or rendered page. [Published package metadata](https://registry.npmjs.org/@fumadocs%2fasyncapi/0.4.4); local evidence: `apps/docs/package.json` and `pnpm-lock.yaml`.

The package explicitly documents both generated physical MDX and virtual source pages, including a TanStack Start example. Virtual pages introduce a second `asyncapi` page type, different loader data, a separate rendering branch, and selective MDX preloading. OpenWA currently assumes every page has an MDX collection path in `apps/docs/src/routes/docs/$.tsx`; generated MDX therefore touches fewer existing concerns. [Official integration](https://www.fumadocs.dev/docs/integrations/asyncapi), [release-pinned integration source](https://github.com/fuma-nama/fumadocs/blob/d6cfc48d62aa9ea413f0fc5033617c0c923681ec/apps/docs/content/docs/%28framework%29/integrations/asyncapi/index.mdx).

Generation is not automatically a filesystem-free runtime. `generateFiles()` produces `<AsyncAPIPage document="schema-id" ... />` plus `_asyncapi.preload` metadata. `createAsyncAPI()` and `generateFiles()` import Node filesystem/path code. The renderer separately accepts either `payload: { bundled }` or `preloaded: { docs }`, so bundled documents can be generated once and passed to a browser-safe renderer without loading schemas during Cloudflare requests. Fumadocs uses its own bundler and checks the `asyncapi` field; it does not depend on the AsyncAPI validator/parser, so successful rendering does not establish specification validity. [Generated MDX source](https://github.com/fuma-nama/fumadocs/blob/d6cfc48d62aa9ea413f0fc5033617c0c923681ec/packages/asyncapi/src/utils/pages/to-text.ts), [renderer payload source](https://github.com/fuma-nama/fumadocs/blob/d6cfc48d62aa9ea413f0fc5033617c0c923681ec/packages/asyncapi/src/utils/create-page.tsx), [document loader source](https://github.com/fuma-nama/fumadocs/blob/d6cfc48d62aa9ea413f0fc5033617c0c923681ec/packages/asyncapi/src/utils/document/load.ts).

**Recommendation (inference):** start with generated MDX in a dedicated event reference directory, a generated bundled-document module, and one `AsyncAPIPage` MDX component that attaches precomputed data. Perform parsing, reference resolution and generation in the generation script; use a limited highlighter configuration because the renderer defaults to full Shiki. Keep Node-only server/generator imports outside browser and Worker request modules. Prefer AsyncAPI 3.1 unless the implementation discovers a specific renderer limitation; Fumadocs models v3 structure and accepts a string version, but this research did not establish complete support for every 3.1-specific feature.

## MCP SDK: protocol support needs source evidence

OpenWA locks **`@modelcontextprotocol/sdk 1.30.1`**; the latest published monolithic package is **1.32.1**. In 1.32.1, `SUPPORTED_PROTOCOL_VERSIONS` ends at 2025-11-25, the server installs `initialize`, and neither the server nor transport implements `server/discover` or the three event methods. Low-level `setRequestHandler(schema, handler)` accepts custom method schemas, but the HTTP transport still rejects unrecognized protocol version headers; the stateful path also requires initialization and its session ID. Adding custom event handlers to v1 does not implement the 2026-07-28 transport and lifecycle. [Published metadata](https://registry.npmjs.org/@modelcontextprotocol%2fsdk/1.32.1), [version constants](https://github.com/modelcontextprotocol/typescript-sdk/blob/ff07b001194fe60ee9deb2121cf119057565796d/src/types.ts), [custom handler registration](https://github.com/modelcontextprotocol/typescript-sdk/blob/ff07b001194fe60ee9deb2121cf119057565796d/src/shared/protocol.ts), [HTTP transport checks](https://github.com/modelcontextprotocol/typescript-sdk/blob/ff07b001194fe60ee9deb2121cf119057565796d/src/server/webStandardStreamableHttp.ts).

The current split packages **`@modelcontextprotocol/server` and `@modelcontextprotocol/core` are 2.3.1**. The server depends only on core 2.3.1 and Zod `^4.2.0`, declares Node `>=20`, supplies workerd/browser/Node shims, and exposes a web-standard `createMcpHandler()` with `fetch(Request): Promise<Response>`. Explicitly select `{ legacy: 'reject' }` for the requested current-only protocol. A hand-constructed v2 server still speaks the earlier protocol by default; the entry point is what opts into 2026-07-28. [Published server metadata](https://registry.npmjs.org/@modelcontextprotocol%2fserver/2.3.1), [release-pinned protocol guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/fcef852f6cdafea07f36cf6fae69b37c8adf85be/docs/migration/support-2026-07-28.md), [HTTP handler source](https://github.com/modelcontextprotocol/typescript-sdk/blob/fcef852f6cdafea07f36cf6fae69b37c8adf85be/packages/server/src/server/createMcpHandler.ts).

Published v2 supports custom method registration through `server.setRequestHandler('method', { params: Schema, result: Schema }, handler)`. Its built-in method catalog does not include webhook MCP Events, so implement the three methods through that extension seam. Native discovery copies the supplied capabilities object; the outbound modern encoder stamps required result/cache/identity fields without parsing discovery capabilities, so a structural extension object containing `events: {}` survives the server's output path. The public capability type/schema does not itself declare `events`; avoid parsing the extended object through that closed schema. This proves an available source-level extension route, not successful ChatGPT discovery. [Custom dispatch source](https://github.com/modelcontextprotocol/typescript-sdk/blob/fcef852f6cdafea07f36cf6fae69b37c8adf85be/packages/core-internal/src/shared/protocol.ts), [native discovery and capability-copy source](https://github.com/modelcontextprotocol/typescript-sdk/blob/fcef852f6cdafea07f36cf6fae69b37c8adf85be/packages/server/src/server/server.ts), [modern outbound encoding](https://github.com/modelcontextprotocol/typescript-sdk/blob/fcef852f6cdafea07f36cf6fae69b37c8adf85be/packages/core-internal/src/wire/rev2026-07-28/codec.ts), [built-in method registry](https://github.com/modelcontextprotocol/typescript-sdk/blob/fcef852f6cdafea07f36cf6fae69b37c8adf85be/packages/core-internal/src/wire/rev2026-07-28/registry.ts).

**Recommendation (inference):** migrate the MCP transport adapter to the current split server package and native modern handler, preserving OpenWA's existing tool definitions and execution kernel. Add the event methods and durable subscriber delivery as OpenWA-owned behavior. This is less work than maintaining a bespoke MCP 2.0 transport; it does not require a legacy dual-protocol fallback. Subscriptions must live outside the per-request server factory so successive calls and server restarts share state.

## Existing OpenWA scope and remaining uncertainty

Issue [#3462](https://github.com/open-wa/wa-automate-nodejs/issues/3462) already scopes generated AsyncAPI contracts for SSE and webhooks. It is planning provenance, not evidence of an implementation. Current source separates listener names, canonical runtime event names and transport envelopes; the shared catalog needs explicit projections for each. Existing docs generation and schema ownership should remain the owners of their respective output rather than exposing raw registry metadata as a wire contract.

These findings do not establish a valid generated OpenWA contract, a Cloudflare-compatible renderer bundle, successful custom SDK dispatch, a verified callback, or delivery into a ChatGPT chat. Those are implementation/runtime acceptance questions. No tests, typechecks, lint checks, builds or CI work were run.

## Authorized mini epic: one PR sharing one catalog

On 2026-10-14 Mohammed authorized planning and implementation of all three integrations in one PR against `master`, with Bumpy minor intent. Mini epic [#3536](https://github.com/open-wa/wa-automate-nodejs/issues/3536) has three linked slices: existing AsyncAPI issue [#3462](https://github.com/open-wa/wa-automate-nodejs/issues/3462), generated Fumadocs reference [#3537](https://github.com/open-wa/wa-automate-nodejs/issues/3537), and MCP Events [#3538](https://github.com/open-wa/wa-automate-nodejs/issues/3538). Both new slices depend on the shared event contract; documentation does not block the runtime slice. All three are delivered together on `work/event-integrations`.

The additional `openai/mcp-extensions` source was considered. Current `@openai/mcp-extensions 0.2.0` supports the split SDK2 through its optional server peer; it supplies UI entrypoints, mentions, files, settings and forms, but no event subscription or signed delivery implementation. The event workflow does not require a UI resource, so this PR uses the native MCP SDK without that dependency. [Pinned package source](https://github.com/openai/mcp-extensions/blob/0d606217705e0e71eb21fff009619b67b80611dc/typescript/package.json), [extension implementation](https://github.com/openai/mcp-extensions/blob/0d606217705e0e71eb21fff009619b67b80611dc/typescript/src/server/extensions.ts).

All three additions are useful. AsyncAPI improves integration discovery for every event consumer; Fumadocs makes that contract readable within the existing docs; MCP Events enables a new workflow such as “watch this WhatsApp conversation and draft a response when a customer asks for a quote.” Build the contract and documentation first, then the runtime subscription layer, within the same PR.

### Slices 1 and 2: event contracts, AsyncAPI and generated reference pages

1. **Add explicit wire-event projections to the existing schema system.** Own this in `packages/schema/src/events/`, co-located with the listener definitions rather than maintaining an unrelated AsyncAPI inventory. Record canonical runtime names, descriptions, payload schemas, applicable transport surfaces and subscriber filter definitions. Reuse listener payload schemas where they describe the emitted data; describe unknown fields honestly. Keep listener callback data distinct from runtime wrapper data. For example, `message` / `onMessage` describes a message, while `message.received` emits `{ ctx, message }`; `session.state.changed` emits a step object with `details.prev` and `details.next`, rather than the listener registry's `{ state, previousState }`. Keep core/API/MCP depending on schema, without importing core into schema.
2. **Generate the contract once.** Add a shared `createAsyncApiDocument()` builder and a small schema-generation script, pinning AsyncAPI 3.1.0. Generate distinct SSE and webhook envelopes around the shared runtime payload definitions. Initial coverage should use the already implemented message, acknowledgement, state, logout and group bridge events, recording optional listener availability explicitly. Add `/meta/asyncapi.json` in `packages/api/src/routes/meta.ts`, using the existing external-base handling, and produce the docs download from the same builder. Describe actual SSE framing, filtering, authentication and lack of history replay; describe the webhook plugin's configured destination, retries and optional delivery journal. User credentials and destinations are never static examples.
3. **Render the generated reference through Fumadocs.** Add `@fumadocs/asyncapi 0.4.4` and Shiki as direct docs dependencies, reusing the already resolved Shiki version if it satisfies the package's range. Extend the docs-generation/copy step with generated MDX, a bundled schema module, CSS and one `AsyncAPIPage` component in `apps/docs/src/components/docs-mdx.tsx`. Attach bundled/preloaded data explicitly. This keeps the existing MDX source and route assumptions intact, and avoids parser/filesystem work on Cloudflare requests. Link the reference and schema download from the event/webhook guides and API explorer. Do not introduce virtual source pages or migrate the documentation framework for this change.

### Slice 3: webhook MCP Events on Easy API

1. **Replace only the MCP transport adapter.** In `packages/mcp/src/adapter/hono-mcp.ts`, use `@modelcontextprotocol/server 2.3.1` and `createMcpHandler(..., { legacy: 'reject' })`. Retain `getMcpToolDefinitions()` and `executeCapability()` as the owners of tool discovery and execution. Advertise a structurally extended capability object containing `events: {}` and register the three event methods with explicit request/result schemas. Keep the authenticated tools/events endpoint on Easy API, with the current API-key scope; public plugin hosting or a new OAuth system is outside this integration.
2. **Wire a catalog-filtered event source into MCP.** Inject a small structural event-source interface from `packages/api/src/createApiServer.ts`, avoiding an API-to-MCP-to-core dependency cycle. MCP subscribes only to catalog entries permitted for public delivery and the authenticated instance; it must not mirror API's unrestricted `onAny` stream. Start with `message.received`, `ack.changed` and `session.state.changed`. Support an exact conversation filter for message/acknowledgement payloads only where their actual fields support it. The received-message event excludes own messages, making it the appropriate default for customer-response workflows. Larger catalogs can be added through the same schema projections later.
3. **Persist subscriptions and delivery jobs outside request factories.** Use a small SQLite subscription store plus an outbound job journal, following the existing webhook journal pattern. Store owner, canonical event, canonical filter arguments, callback, secret and expiry; repeated subscribe calls update a deterministic subscription identity. Recheck scope and expiry before enqueueing or sending, and make unsubscribe idempotent. Pending delivery retries should survive a restart, but the first version does not retain a general WhatsApp event history: return `cursor: null` and do not claim recovery of events missed while OpenWA is down.
4. **Implement the MCP-specific sender using existing queue machinery.** Reuse `ScopedTaskQueue` from `@open-wa/runtime-core`, and use `standardwebhooks` for signatures. The existing webhook sender has one configured URL, a different fixed envelope and plain `fetch`, so passing MCP events through it unchanged would be incorrect. Serialize each MCP event once, retain its unique event ID across retries, take occurrence time from the runtime event, and sign with a fresh delivery timestamp on each attempt. Verify callbacks with the signed challenge, connect only to validated public HTTPS addresses, reject redirects, and stop retrying `410`/`413`. Keep payloads below 256 KiB; a compact message projection can use the existing `getMessageById` tool for full records. Document the MCP projection separately from the full SSE/webhook payload, while generating its schemas from the same catalog.
