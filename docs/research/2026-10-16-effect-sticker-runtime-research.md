# Effect documentation relevant to the sticker runtime

Read on 2026-10-16. This is documentation research requested by Mohammed, not an implementation or adoption decision. No dependencies, application code, tests, typechecks, lint checks, builds, workflows, or benchmarks were added or run.

## Version and source boundary

The repository currently pins Effect and its platform packages to **4.0.2** in `pnpm-workspace.yaml`; the public [`effect/latest` manifest](https://registry.npmjs.org/effect/latest) returned **4.0.5** when read on 2026-10-16. No upgrade is proposed or performed. The website has a separate v4 documentation tree; several unversioned resource-management links redirect to v3. Use the explicit `/docs/v4/` pages below and the pinned **effect@4.0.2** source commit [`269a7c864351231d42e6e95b7fa8f32050df3691`](https://github.com/Effect-TS/effect/tree/269a7c864351231d42e6e95b7fa8f32050df3691). These are released v4 sources, not the earlier v4 beta API.

The core resource primitives discussed below are marked stable in that release. The worker transport, runner, transferable, and worker-backed RPC APIs are explicitly marked **unstable**, even though they ship inside a stable Effect release. Their current v4 paths are `effect/workers/*` and `effect/rpc/*`; do not copy the older v3 `@effect/platform/Worker.makePool` examples into this workspace. [Pool module](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/Pool.ts#L1-L12), [Worker module](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/workers/Worker.ts#L1-L12), [worker RPC constructor](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/rpc/RpcClient.ts#L1276-L1300).

## Resource ownership and cleanup

`Effect.acquireRelease` couples a successful acquisition with a scope finalizer. Acquisition is uninterruptible, and the release runs when the owning scope closes, including failure and interruption. `Effect.scoped` supplies and closes an operation's scope; default finalizers run in reverse acquisition order. That maps to worker termination, decoder/image disposal, and temporary resources that must be released together. `Effect.ensuring` attaches cleanup to one effect; `Effect.onExit` also receives its outcome. Neither primitive removes the need to implement the actual browser, worker, and native cleanup actions. [Scope](https://effect.website/docs/v4/resource-management/scope/), [resource management introduction](https://effect.website/docs/v4/resource-management/introduction/).

Closing an arbitrary resource scope does **not** itself interrupt every unrelated task using that resource. Ownership of running fibers must also be explicit. The appropriate job scope must outlive the render, and a backend scope must outlive every active borrower; otherwise cleanup can race outstanding work. This is the distinction between owning resources and owning execution. [Scope: manually creating and closing scopes](https://effect.website/docs/v4/resource-management/scope/#manually-create-and-close-scopes).

`Layer` is a constructor and dependency graph for internal services, not a caller-facing lifecycle requirement. In v4, `Layer.effect` can construct a scoped service whose implementation uses `acquireRelease` or `addFinalizer`; the old separate `Layer.scoped` form is unnecessary. A shared layer instance is memoized within a build graph; separately providing it inside every call rebuilds it unless a shared memo map/runtime owns it. Therefore, wrapping each `createSticker` call in its own newly provided renderer layer would lose burst reuse. [Managing layers](https://effect.website/docs/v4/requirements-management/layers/), [layer memoization](https://effect.website/docs/v4/requirements-management/layer-memoization/).

## A hidden runtime can retain the public Promise API

`ManagedRuntime.make(layer)` remains a stable v4 API. It lazily builds and caches the service context across calls and exposes `runPromise`, so `createSticker(input, job): Promise<StickerResult>` can remain unchanged while all Effect machinery stays inside the package. Disposing the managed runtime releases its services; it is permanently unusable afterward, so an automatically restarted runtime must be a fresh instance rather than a disposed instance being reused. The constructor does not add an idle policy by itself. [Runtime documentation](https://effect.website/docs/v4/runtime/), [ManagedRuntime lifecycle contract](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/ManagedRuntime.ts#L235-L253).

The pinned implementation tracks managed run fibers in an internal scope, interrupts and awaits them on disposal, then closes its owned scopes. This is stronger than merely closing an arbitrary scope, but it still depends on asynchronous/native operations honoring interruption or being explicitly terminated by their finalizer. [ManagedRuntime implementation](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/ManagedRuntime.ts#L291-L357).

## Reuse during bursts and release when idle

Two stable primitives address different lifetimes:

- **`RcRef` shares one lazily acquired resource.** Each `get` borrows it for the current scope, and `idleTimeToLive` retains it after the final borrower leaves, then releases it. Later demand acquires another instance. This closely matches one hidden sticker host that should remain warm for a burst and disappear when idle. A finite idle TTL runs release in a background fiber, so it is not a guarantee that the last job waits for disposal. `invalidate` makes future borrowers acquire a fresh resource without revoking existing borrowers. [RcRef contract](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/RcRef.ts#L114-L250).
- **`Pool` shares a bounded number of resource instances.** `makeWithTTL` has minimum and maximum sizes, per-item concurrency, utilization, and idle reclamation. A pool can use `min: 0` to release every renderer when idle and `concurrency: 1` for exclusive use of each CPU worker. `Pool.get` waits at capacity and returns its lease when its scope closes; `Pool.use` returns it when one operation finishes. Invalidating a broken instance prevents future reuse and allows lazy replacement. [Pool construction](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/Pool.ts#L251-L325), [borrowing](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/Pool.ts#L439-L527), [invalidation](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/Pool.ts#L766-L799).

These are alternatives or distinct ownership layers, not a requirement to stack `RcRef`, `Pool`, and a new runtime manager around the same resource. The simplest useful split is one hidden execution boundary and one owner for the actual renderer/worker lifecycle. The default pool TTL strategy measures idle time after the last borrower releases an item, but periodic checks mean retirement can take up to **twice** the configured TTL. It cannot promise an exact 60-second cleanup deadline. [Pool TTL details](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/Pool.ts#L260-L274).

Pool size bounds the number of resource instances, not the number or total bytes of waiting jobs. Input loading and frame expansion must remain behind whichever execution admission mechanism owns the burst. Merely replacing the present worker set with `Pool` would not make arbitrarily large input bursts memory-bounded.

The pinned `RcRef` implementation also handles concurrent bootstrap and bootstrap failure: first callers share one acquisition fiber, a failed or interrupted acquisition closes its partial scope and resets the reference to empty, and a later caller can acquire again. Canceling one waiter does not cancel acquisition needed by other waiters; acquisition is abandoned when all waiters leave. This matters because a rejected cached bootstrap Promise can otherwise poison all subsequent sticker calls. [RcRef acquisition implementation](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/internal/rcRef.ts#L126-L194).

## Admission, cancellation, and independent failures

Effect values describe work lazily, so the code can acquire capacity before reading files, downloading inputs, copying buffers, decoding frames, or starting a renderer. `Queue.bounded` suspends offers while full; its dropping/sliding alternatives discard items and therefore do not fit a sticker API whose caller expects a result for every submitted job. Semaphore permits cap active work and are returned after failure or interruption. Neither mechanism alone bounds the number of suspended producers or the input objects and output arrays retained by callers. [The Effect type](https://effect.website/docs/v4/getting-started/the-effect-type/), [queues](https://effect.website/docs/v4/concurrency/queue/), [semaphores](https://effect.website/docs/v4/concurrency/semaphore/).

`Effect.all` and `Effect.forEach` fail fast by default. Independent jobs need their errors captured inside the job, for example as an `Exit`, so one invalid image does not interrupt unrelated consumer siblings. Consumers should belong to the shared service's scope, while each job has its own cancelable lifetime. Child fibers inherit a parent's lifetime, so accidentally attaching long-lived consumers to one caller would make that caller's completion shut down shared work. `Deferred` provides one completion result, and `Ref` / `SynchronizedRef` cover shared state and effectful atomic updates where needed. These abstractions are tools for existing ownership requirements, not reasons to add public initialization or readiness checks. [Basic concurrency](https://effect.website/docs/v4/concurrency/basic-concurrency/), [fibers](https://effect.website/docs/v4/concurrency/fibers/), [error accumulation](https://effect.website/docs/v4/error-management/error-accumulation/), [Deferred](https://effect.website/docs/v4/concurrency/deferred/), [Ref](https://effect.website/docs/v4/state-management/ref/), [SynchronizedRef](https://effect.website/docs/v4/state-management/synchronizedref/).

Interruption is cooperative. Wrapping a Promise does not stop its underlying operation; `tryPromise`'s signal or an asynchronous callback's cancellation cleanup must reach the download, decoder, or worker termination action. A timeout interrupts its Effect, but uninterruptible finalizers can make completion exceed that nominal timeout. A CPU-bound synchronous function also needs actual worker isolation or deliberate yielding; Effect fibers alone cannot move it to another CPU thread. Keep `Effect.run*` at the Promise-facing boundary and normalize failures back to the existing `StickerError` contract. [Creating effects](https://effect.website/docs/v4/getting-started/creating-effects/), [running effects](https://effect.website/docs/v4/getting-started/running-effects/), [timing out](https://effect.website/docs/v4/error-management/timing-out/), [expected errors](https://effect.website/docs/v4/error-management/expected-errors/), [unexpected errors](https://effect.website/docs/v4/error-management/unexpected-errors/).

## Caching and retry policies are separate concerns

Caching a result is different from owning a resource. `Effect.cached` retains the computed outcome, including failure/interruption, so using it blindly for renderer bootstrap can retain an unusable result. `Cache` supports bounded cached lookups and TTLs, but also caches failures; interrupted entries are removed. A cached-value age is not an idle resource lease, and expiration does not automatically finalize arbitrary objects. Owned renderers therefore need an ownership primitive such as `RcRef` or `Pool`, rather than a generic memoization wrapper. [Caching effects](https://effect.website/docs/v4/caching/caching-effects/), [Cache](https://effect.website/docs/v4/caching/cache/).

Retries and schedules can express bounded attempts and delays for transient resource downloads or rendering acquisition. They should not indiscriminately retry invalid input, deterministic recipe failures, or an unknown WhatsApp send outcome, which could duplicate a message. Transport restart, renderer replacement, render retry, and message submission are distinct operations with different safety properties. [Retrying](https://effect.website/docs/v4/error-management/retrying/), [using schedules](https://effect.website/docs/v4/scheduling/using-schedules/), [choosing and combining schedules](https://effect.website/docs/v4/scheduling/choosing-and-combining-schedules/).

Schedules coordinate in-memory work; they do not create durable queues. `Schedule.spaced` waits between completed work and its next repetition, which is useful for cleanup or transient loading policies but not an exact wall-clock scheduler. Recovery should target recognized transient errors rather than retrying interruptions, defects, and every job failure alike. [Using schedules](https://effect.website/docs/v4/scheduling/using-schedules/), [retrying](https://effect.website/docs/v4/error-management/retrying/).

## Streams, fiber tracking, and observations

For a future batch API, streams provide pull-based input and bounded `mapEffect` concurrency, so files can be consumed as capacity becomes available. A bounded buffer is still needed when producers run ahead, and ordered output can retain completed results while an earlier item is slow. Capturing each job's failure remains necessary when the batch should continue. Debounce and switch/replacement operators suit a live sticker preview where the newest edit supersedes an old one; they must not discard explicit requests to create or send stickers. [Stream introduction](https://effect.website/docs/v4/stream/introduction/), [stream operations](https://effect.website/docs/v4/stream/operations/), [resourceful streams](https://effect.website/docs/v4/stream/resourceful-streams/).

`FiberSet` and `FiberMap` tie many background fibers to a scope and remove finished fibers from tracking. Replacing a keyed fiber interrupts its predecessor, so that behavior belongs to replaceable previews rather than independent jobs. The platform `runMain` helper is an application entry point; a library should not take ownership of its consumer's process signals merely to manage renderer resources. [Tracking fibers](https://effect.website/docs/v4/observability/tracking-fibers/), [platform runtime](https://effect.website/docs/v4/platform/runtime/).

If measurements are later requested, queue-depth and active-job gauges, latency histograms, and spans around queue wait, input loading, rendering, and cleanup can distinguish a saturated pool from slow decoding or teardown. Effect provides those instruments without requiring a newly commissioned telemetry stack. This research did not add instrumentation or run measurements. [Metrics](https://effect.website/docs/v4/observability/metrics/), [logging](https://effect.website/docs/v4/observability/logging/), [tracing](https://effect.website/docs/v4/observability/tracing/).

The style guidance supports a small public operation with services acquired at construction and Effect execution at the application/library boundary. There is no reason to make users learn layers, scopes, fibers, or disposal to create a sticker. [Guidelines](https://effect.website/docs/v4/code-style/guidelines/), [managing layers](https://effect.website/docs/v4/requirements-management/layers/), [running effects](https://effect.website/docs/v4/getting-started/running-effects/).

## CPU workers and platform boundaries

Effect's worker abstractions wrap actual platform endpoints; they do not convert ordinary fibers into CPU threads. In v4 the parent side is `effect/workers/Worker` plus `NodeWorker` or `BrowserWorker`; the worker entry point uses `effect/workers/WorkerRunner` plus the matching platform runner. A worker handler and spawning callback still have to exist. The Node adapter supports real `node:worker_threads` workers and IPC child processes; the browser adapter supports `Worker`, `SharedWorker`, and `MessagePort`. [Worker](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/workers/Worker.ts), [WorkerRunner](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/workers/WorkerRunner.ts), [NodeWorker](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/platform/node/src/NodeWorker.ts), [BrowserWorker](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/platform/browser/src/BrowserWorker.ts).

The higher-level v4 worker pool is `RpcClient.makeProtocolWorker` / `layerProtocolWorker`, backed by the stable `Pool` implementation. It supports fixed `size` or elastic `minSize`, `maxSize`, and `timeToLive`, with optional per-worker concurrency and utilization. The server uses `RpcServer.layerProtocolWorkerRunner`. Adopting it also means adopting the worker RPC protocol and matching schemas; it is not a drop-in owner for the existing arbitrary `worker.mjs` message format. Its built-in worker transport retry restarts a failed worker run every second; that is separate from retrying an application render. [Client worker protocol](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/rpc/RpcClient.ts#L1276-L1475), [server worker protocol](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/rpc/RpcServer.ts#L1445-L1521).

Shutdown semantics differ. The Node parent sends a graceful close message and waits up to five seconds before terminating the worker. The browser parent's documented contract sends close and removes listeners, but **does not terminate dedicated workers created by its spawner**. An internal browser worker owner still needs an explicit termination finalizer if releasing all CPU/memory resources is required. Do not assume platform abstraction alone provides identical process teardown. [Node shutdown](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/platform/node/src/NodeWorker.ts#L24-L67), [browser shutdown contract](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/platform/browser/src/BrowserWorker.ts#L19-L69), [Node runner](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/platform/node/src/NodeWorkerRunner.ts), [browser runner](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/platform/browser/src/BrowserWorkerRunner.ts).

`effect/workers/Transferable` can mark backing buffers, image pixels, and ports for the native `postMessage` transfer list, avoiding a clone of large data. Its transfer wrappers operate through schema encoding and do not automatically change existing postMessage calls. Caller-owned buffers also require an ownership decision because a real transfer moves their backing storage; keep that decision internal to the renderer boundary. [Transferable module](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/workers/Transferable.ts#L1-L12), [Uint8Array transfer schema](https://github.com/Effect-TS/effect/blob/269a7c864351231d42e6e95b7fa8f32050df3691/packages/effect/src/workers/Transferable.ts#L192-L202).

## Relevance to the current sticker implementation

Source inspection only: `packages/stickers/src/lifecycle.mjs` already owns a waiting job map, execution concurrency, AbortControllers, a two-minute execution timeout, and 60-second host idle cleanup. `packages/stickers/src/library.mjs` already owns actual Node worker threads, a second queue, a maximum of two workers adjusted for CPU availability, worker failure replacement, termination, and its own idle timers. `packages/stickers/src/index.mjs` exposes the Promise-based singleton. The sticker package currently declares no Effect dependency. These are observations of source, not runtime or load-test results.

The relevant Effect concepts are therefore existing mechanisms to understand before choosing any replacement: safe finalization, one internal lifecycle owner, scoped borrowing, bounded active work, cancellation, and real CPU isolation. Effect adoption would be an internal implementation choice. Users should continue to call `createSticker(input, { author, pack, ... })` without initializing, disposing, or importing an Effect runtime. No refactor was authorized or performed in this documentation-reading task.
