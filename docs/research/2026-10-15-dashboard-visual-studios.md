# Visual message and sticker studios for the self-hosted Neo dashboard

Implementation started on 2026-10-16 under [#3555](https://github.com/open-wa/wa-automate-nodejs/issues/3555), after the Paper consolidation and copy passes. The research below describes the earlier source snapshot. The walkthrough record includes the current implementation scope and evidence limits.

Research date: 2026-10-15. This is design research for `apps/dashboard-neo`, the dashboard served by an operator's own OpenWA instance. The component findings below come from reading every implementation in the four directories listed in the inventory and inspecting current first-party component catalogues. No implementation, package installation, tests, builds, lint, typechecks, or application runs were performed for this note. Product recommendations are marked as recommendations; upstream catalogue availability does not mean a component is installed locally.

The strongest design is two focused visual tools, **Interactive messages** and **Sticker studio**, sharing a live preview and an always-visible **Copy code** action. Use the existing BoardUI appearance and Base UI controls, adding a few source components where useful. The libraries supply controls and presentation; OpenWA must own the message model, WhatsApp-specific preview, code generation, and sticker rendering behavior.

## What the visual experiences should do

### Interactive messages

**Recommendation:** make a structured visual composer rather than an unrestricted document editor. Start with a useful example, offer visible message-type cards, and keep editable content beside a WhatsApp-style preview. Clicking a header, action, list row, or carousel card in the preview selects its corresponding inspector field. Add, duplicate, remove, and move controls should remain visible, with keyboard-accessible move-up/down actions even if drag handles are added later.

Model the preview as a local simulation: pressing a quick reply records the selected ID; opening a list/form shows the receiver's choices; carousel cards can be browsed. URL/call/copy actions should show what they would do without performing real actions during preview. Mark this as a preview because web simulation cannot establish how every WhatsApp client renders a message. The custom domain renderer composes the upstream message/bubble/control pieces; no inspected library ships this WhatsApp designer.

Keep **Copy code** in the tool header and beside the code pane. Preview, copied code, and any eventual **Send to chat** action must consume the same canonical draft rather than independently reconstruct the payload. A visible language/transport choice can expose Node/TypeScript and HTTP examples where supported by the actual API. A placeholder recipient is appropriate for copied examples; a real send uses an explicitly selected chat. Inline schema errors should name the field and explain the correction, rather than disappear into a toast.

Use an ordinary textarea initially, optionally with a small WhatsApp-aware formatting toolbar that transforms the supported text syntax. A general HTML rich-text editor would need extra conversion rules and could suggest formatting the transport cannot represent. The message schema and current API implementation must determine exactly which message types, field limits, and button combinations the composer offers.

### Sticker studio

**Recommendation:** organize the tool around **Choose media → Shape and style → Preview → Copy code / Download**, with immediate visual feedback. A transparent checkerboard canvas should show the sticker without a chat bubble, with an optional chat-context view. Keep file selection and the main output actions obvious. Use a searchable effect gallery, numeric controls beside sliders, and metadata fields for the supported pack and author labels. The current job contract has no caller-supplied emoji metadata field.

An output viewport, fit/fill behavior, animated playback, trim controls, effect rendering, and output-size reporting are custom application work. Initial framing should expose the existing contain/cover and circle settings; arbitrary crop handles, free placement, and frame thumbnails would require more application and recipe work. Use Base UI controls around that work, but do not describe a Slider as a complete video editor or a Carousel as a timeline. Represent reading, decoding, rendering, encoding, cancellation, and failure from actual work; picking a local file does not constitute a server upload.

The renderer should consume one draft recipe and source for both preview and export. Local `blob:` preview URLs cannot be pasted into another process, so copied code needs a portable source or an intentionally exported source/recipe pair. Use the real sticker package's rendered WebP for preview rather than approximate the selected effects with CSS. A send can rerender the same source and job in the API host's selected backend; that is recipe consistency, not a guarantee of byte-identical browser and host output.

## Recommended workspace and editing model

Add **Message studio** and **Sticker studio** directly to Neo's Developer tools navigation, with proposed routes `/studio/messages` and `/studio/stickers`. Keep the existing generic API playground available for arbitrary methods. The inspected [sidebar](/Users/Mohammed/projects/tools/wa/apps/dashboard-neo/src/components/app-sidebar.tsx) and [playground](/Users/Mohammed/projects/tools/wa/apps/dashboard-neo/src/routes/playground.tsx) already establish the shell and session connection, but the playground represents every argument with a text input and copies only the execution response; it does not supply a visual authoring model or code exporter.

Use the same three regions in both studios: **controls and structure → editable preview → generated code**. Put a useful example/template strip above them. On a narrow screen, expose Design, Preview, and Code as panels rather than compress three columns. Keep the primary copy action available in the page header. This is a layout recommendation, not an implemented route.

For messages, clicking preview text or a button label should open inline editing; selecting a header, question, or carousel card should reveal its relevant fields in the inspector. Preview interactions need distinct Design and Try behavior so pressing a button can either edit it or simulate the recipient's choice without ambiguity. Start with visible text controls and a small supported-formatting toolbar; a general HTML editor would introduce capabilities WhatsApp does not render.

For stickers, make the chosen effects an ordered stack with per-instance controls, duplicate/remove actions, and accessible move-up/down controls. Dragging can supplement those actions. Keep instance identity separate from effect name because the API permits the same effect more than once. Templates should be real message documents or sticker jobs, so choosing “Support menu”, “Product choices”, “Appointment confirmation”, or “Comic + sparkle” immediately produces an editable, exportable example.

## Interactive API: what the designer can actually expose

The current [interactive schema](/Users/Mohammed/projects/tools/wa/packages/schema/src/interactive.ts) deliberately defines a portable JSON document shared by SDK, HTTP, and builders. Its `InteractiveContentSchema` and `defineInteractiveMessage` should own document validation; preview selection, panel state, drag IDs, and draft names belong outside that strict wire document. Keep recipient/session selection outside the content as well. Do not create a second builder format and translator for fields already represented by this schema.

| Current document | Visual editor and receiver preview | Generated response example |
| --- | --- | --- |
| `buttons` with reply actions | Edit body/footer, optional text/image/video/document header, visible button labels, and stable reply IDs. | `onInteractiveResponse` with `type: 'reply'` and the selected `id`. |
| `buttons` with URL/call/copy actions | Offer an action-family choice, then edit link destinations, phone numbers, and copy codes beside their labels. The schema rejects mixing these actions with replies. | Show the intended action locally; do not invent URL-open, call-click, or code-copy receipt events. |
| `list` | Add and reorder sections/rows; edit the opening button and the receiver's sectioned picker. Row IDs must be unique across all sections. | `type: 'list'` with the chosen row ID. |
| `form` | Add single-select and multi-select questions/options; preview choosing and submitting answers. Expose `allowCustomAnswer` where useful. There are no arbitrary text/date/upload question types or required/minimum-choice settings in this contract. | `onFormResponse` with `answers` keyed by stable question IDs; values are an option string or array. |
| `carousel` | Browse and reorder image cards; edit each card's image, body, and actions. Generate distinct reply IDs by default so applications can identify a card's choice. | The same reply response contract for reply actions; no made-up carousel analytics. |
| `booking` | Edit date/time with an explicit time zone, location, URLs, contact details, description, labels, and optional CTA actions. Serialize time as an ISO timestamp with an offset. Preview opening the details. | Explain the available actions; the current response union has no dedicated booking-confirmed event. Booking content has no custom header/image. |
| `native` | Offer an advanced native-action JSON editor outside the normal template flow. Preserve schema validation without presenting arbitrary native actions as proven receiver features. | Unknown native responses remain inspectable with their raw parameters and possible parse error. |

Do not inherit the three-button limit from deprecated methods: the new typed action schema has its own rules. Preserve IDs when labels change or rows move, because integrations route responses by those IDs. Polls can be a later separate editor backed by `sendPoll` and `onPollVote`; they are not form submissions, because votes can change or be removed. Sources: [interactive definitions](/Users/Mohammed/projects/tools/wa/packages/schema/src/interactive.ts), [messaging methods](/Users/Mohammed/projects/tools/wa/packages/schema/src/methods/messaging.ts), [poll schemas](/Users/Mohammed/projects/tools/wa/packages/schema/src/polls.ts), and [public guide](/Users/Mohammed/projects/tools/wa/apps/docs/content/docs/guides/interactive-messages.mdx).

The code pane should expose **TypeScript/JavaScript**, **HTTP/cURL**, and **JSON**, plus a Send/Handle response choice where the message produces a response. Generate every output from the parsed content document. The existing calls are `client.sendInteractive(to, content)` and `POST /api/messages/sendInteractive` with `{ to, content }`; response subscriptions must be shown before sending. HTTP examples should use an environment-variable API-key placeholder, rather than copy the dashboard's actual credential. A small snippet may assume an existing `client`; label that assumption and offer a separate complete connection example. Sources: [method registration](/Users/Mohammed/projects/tools/wa/packages/schema/src/methods/interactive.ts), [client implementation](/Users/Mohammed/projects/tools/wa/packages/client/src/methods/interactive.ts), and [guide](/Users/Mohammed/projects/tools/wa/apps/docs/content/docs/guides/interactive-messages.mdx).

An editable JSON mode can round-trip into the visual editor after schema parsing. Display invalid field paths inline and mark the current draft invalid rather than silently sending an older valid draft. Exported media must use reachable URLs or data URLs, or accompany explicit saved assets: a browser `File` name and `blob:` preview URL do not identify a file on the API host.

Preview choices should produce a clearly labelled **simulated response** beside the actual handler snippet. A real send should have a separately labelled response area. The current dashboard [useEvents hook](/Users/Mohammed/projects/tools/wa/apps/dashboard-neo/src/lib/hooks/use-events.ts) does not collect `interactive.response`, and the [SocketClient mapping](/Users/Mohammed/projects/tools/wa/packages/socket-client/src/SocketClient.ts) does not map the interactive listener convenience names. The studio can explicitly subscribe to the canonical `interactive.response` stream and read `payload.response`; the local SDK's listener facade already unwraps that payload. Do not assume the dashboard's generic event list implements the SDK callback semantics. Sources: [event transforms](/Users/Mohammed/projects/tools/wa/packages/client/src/events/EventManager.ts) and [listener methods](/Users/Mohammed/projects/tools/wa/packages/client/src/Client.ts).

Keep authoring, simulation, and export available without a WhatsApp connection or paid license. Actual interactive sending uses the existing session access rules: the [method metadata](/Users/Mohammed/projects/tools/wa/packages/schema/src/methods/interactive.ts) requires Insiders or higher, and the client reports when the required runtime sender is absent. Reuse [health](/Users/Mohammed/projects/tools/wa/apps/dashboard-neo/src/lib/hooks/use-health.ts) and [license](/Users/Mohammed/projects/tools/wa/apps/dashboard-neo/src/lib/hooks/use-license.ts) information already available in Neo; a tier label alone does not prove recipient support. An outgoing message ID means submission, not confirmed rendering or interaction. These are current API semantics, not a request to introduce additional readiness gates.

## Sticker API: real capabilities, recipe export, and reuse

The inspected [sticker README](/Users/Mohammed/projects/tools/wa/packages/stickers/README.md) and [recipe definitions](/Users/Mohammed/projects/tools/wa/packages/stickers/src/definitions.mjs) describe **62 implemented shared effects**. Build the shelf from `listEffects({ availableOnly: true })`, with backend capability information where relevant, rather than from the larger historical inventory. Suggested browse groups are appearance (comic, tint, pixelate), motion (sparkle, shake, squish), framing/masks (polaroid, stars, stripes), and text-bearing presets (polaroid caption and newspaper headline). These groups are UI recommendations, not a new package taxonomy. Sources: [catalogue](/Users/Mohammed/projects/tools/wa/packages/stickers/src/catalogue.mjs) and [public types](/Users/Mohammed/projects/tools/wa/packages/stickers/src/index.d.mts).

Expose the existing recipe controls: up to eight ordered effects, contain/cover, circle, background, quality, trim in source milliseconds, FPS, loop count, author, and pack. Let a still image gain motion through animated effects and let `freeze` keep a frame at its position in the stack. Show the actual output's animation, frame count, duration, dimensions, and bytes when available; do not populate them with estimates disguised as render results. Sources: [planner](/Users/Mohammed/projects/tools/wa/packages/stickers/src/planner.mjs), [definitions](/Users/Mohammed/projects/tools/wa/packages/stickers/src/definitions.mjs), and [result types](/Users/Mohammed/projects/tools/wa/packages/stickers/src/index.d.mts).

The first supported file choices should be PNG/JPEG/GIF/WebP, including implemented animated paths. AVIF depends on browser capabilities. MP4 conversion, background removal, and unported historical effects should not appear as working tools. The output profile is 512×512, up to 120 frames and 10 seconds, with maximum input 20 MiB and static/animated output budgets of 100,000/512,000 bytes; rendering reserves 4,096 bytes for final metadata. Read these values from `STICKER_PROFILE`. They are ceilings, not targets. Sources: [coverage](/Users/Mohammed/projects/tools/wa/packages/stickers/README.md), [profile](/Users/Mohammed/projects/tools/wa/packages/stickers/src/profile.mjs), [planner](/Users/Mohammed/projects/tools/wa/packages/stickers/src/planner.mjs).

Use `createSticker(source, job)` for the preview and **Download WebP**, `client.sendSticker(to, input, job)` for the SDK example, and `POST /api/messages/sendSticker` with `{ to, input, job }` for HTTP. Also offer a downloaded job JSON and `openwa-sticker source.png --job sticker-job.json --output sticker.webp` for CLI use; `--effects` alone cannot express per-effect options or trim settings. HTTP inputs accept a data URL or HTTP(S) URL, while the local library and SDK additionally accept bytes, Blob, and local filenames. Never copy a browser object URL into an integration snippet. Sources: [HTTP schema](/Users/Mohammed/projects/tools/wa/packages/schema/src/methods/messaging.ts), [SDK sender](/Users/Mohammed/projects/tools/wa/packages/client/src/stickers.ts), [library types](/Users/Mohammed/projects/tools/wa/packages/stickers/src/index.d.mts), and [CLI](/Users/Mohammed/projects/tools/wa/packages/stickers/src/cli.mjs).

Sending should use the original source and the recipe once. Applying the effects to a rendered preview and then sending that preview with the effects again would apply the stack twice. The current SDK can rerender the source/job in its browser or standalone renderer; sending pre-rendered bytes is not a promise of byte preservation because `sendSticker` still runs the renderer. Render-only downloads and actual WhatsApp sends should remain separate actions. Author and pack are editable labels; donor application links are finalized by the private send patch and are not studio inputs. `sendRawMessage` rejects sticker payloads. Sources: [SDK sender](/Users/Mohammed/projects/tools/wa/packages/client/src/stickers.ts), [interactive sender](/Users/Mohammed/projects/tools/wa/packages/client/src/methods/interactive.ts), and [sticker package description](/Users/Mohammed/projects/tools/wa/packages/stickers/README.md).

The existing [sticker concept controller](/Users/Mohammed/projects/tools/wa/concepts/11-sticker-studio/src/lib/studio.ts) is useful source for local uploads, ordered effects, lazy package loading, debounced rendering, stale-result suppression, and object-URL cleanup. Port those patterns into React and the Neo components. Do not copy its entire controller: it hardcodes 14 effect choices and an older CLI version, prohibits duplicate effects through toggle semantics, and globally patches `OffscreenCanvas.prototype.convertToBlob`. The current [browser backend](/Users/Mohammed/projects/tools/wa/packages/stickers/src/browser.mjs) still encodes its capability-probe canvas without first acquiring a rendering context, matching the failure addressed by that concept workaround. Fix the library probe when implementing the studio instead of carrying the global patch into Neo. This is a source finding; the failing path was not run in this research.

Two implementation seams need explicit ownership. First, effect descriptors expose defaults but no public per-option bounds/schema; the bounds live inside the planner. Move that option information into a shared descriptor/schema before generating sliders and number fields, so the studio and renderer do not maintain competing rules. Second, a dashboard browser cannot run the package's Node worker backend. If the studio needs complete host-rendered previews for jobs its own browser cannot execute, add a render-only host operation using the same sticker runtime; no such API operation was found in this source pass. Browser rendering may download pinned fonts, and host rendering downloads pinned resources on demand, so “local” should not be presented as guaranteed offline operation. Sources: [descriptor types](/Users/Mohammed/projects/tools/wa/packages/stickers/src/index.d.mts), [planner](/Users/Mohammed/projects/tools/wa/packages/stickers/src/planner.mjs), [runtime selection](/Users/Mohammed/projects/tools/wa/packages/stickers/src/index.mjs), [Node worker](/Users/Mohammed/projects/tools/wa/packages/stickers/src/library.mjs), and [resource manifest](/Users/Mohammed/projects/tools/wa/packages/stickers/src/resources.mjs).

## Suggested implementation sequence

1. **Make the shared authoring workspace.** Add the two Neo routes, the common controls/preview/code layout, real example drafts, schema-derived message state, and transport-specific code generation. Keep the generic playground intact.
2. **Complete the interactive-message designer.** Start with replies and lists, then add forms, image carousels, bookings, and media headers using their existing schema. Include receiver simulation and the matching handler code as part of each type's authoring experience.
3. **Bring the real sticker renderer into the studio.** Fix the package probe, expose shared effect-option metadata, and use the executable catalogue for the effect shelf, ordered stack, animation controls, WebP download, and SDK/HTTP/CLI recipe export. Add host preview rendering only if that scope is needed.
4. **Connect the existing runtime actions.** Reuse Neo's connection and recipient patterns for an explicit send, and expose canonical interactive responses in the studio. Keep simulated responses visibly separate from actual runtime events.

This sequence is a recommendation for future implementation. The present task produced this research note only, without running the dashboard, sending messages, or changing any runtime code. Any new injected runtime behavior would belong in the separate patch sources before WAPI is locked; the immutable browser asset is outside this design work.
