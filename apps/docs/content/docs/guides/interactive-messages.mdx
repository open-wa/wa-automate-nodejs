# Interactive messages

Interactive messages need an applied [license](/docs/licensing/pricing). You describe each message as one JSON document and send it from the SDK, the Easy API or a message builder. `sendInteractive` returns the message ID, which confirms the send, not that the recipient saw or tapped it. The examples assume a `client` from `create()`.

```ts
import { defineInteractiveMessage } from '@open-wa/wa-automate';

const message = defineInteractiveMessage({
  type: 'buttons',
  body: 'How can we help?',
  actions: [
    { type: 'reply', id: 'sales', label: 'Talk to sales' },
    { type: 'reply', id: 'support', label: 'Get support' },
  ],
});
client.onInteractiveResponse(response => {
  if (response.type === 'reply') console.log(response.id, response.originalMessageId);
});
const messageId = await client.sendInteractive('PHONE_NUMBER@c.us', message);
```

Over the Easy API, send `POST /api/messages/sendInteractive` with `{ "to": "PHONE_NUMBER@c.us", "content": message }` and your `X-API-Key` header. Both paths validate the document the same way. The [booking confirmation recipe](/docs/build/booking-confirmation) puts this together end to end.

## The message document

`version: 1` is optional and names the version of the document format, so new content types can arrive without changing existing documents. Unknown fields are rejected, so a misspelled property fails instead of disappearing. `InteractiveContentSchema` and the content and action schemas are exported by `@open-wa/schema`, and `defineInteractiveMessage` and `InteractiveContentSchema` are also exported by `@open-wa/wa-automate`. A message builder should store this document as it is, with no separate format of its own.

Every content variant has `type`, `body` and optional `footer`. Use application-defined stable IDs for replies, list rows, questions and options. Labels can change without changing how your application identifies the response. Lists default to “Choose an option” and bookings to “View booking” when `buttonLabel` is omitted. `defineInteractiveMessage` fills those defaults and retains the specific content type, so a list remains a list in TypeScript autocomplete.

| Type | Content |
| --- | --- |
| `buttons` | `actions`, optional `header` |
| `list` | `sections`, optional `buttonLabel` and `title` |
| `form` | `questions`, optional `title` |
| `carousel` | `cards`, each with an image `header`, `body` and `actions` |
| `booking` | `booking`, optional `buttonLabel`, `title` and additional CTA `actions` |
| `native` | Native `actions` and optional `parameters`/`header` for advanced extensions |

### Actions and headers

![Illustration of separate URL, call and copy actions](/images/interactive/cta-actions.png)

*Offer a website link, phone action or copyable code. Keep these separate from reply buttons.*

```ts
{ type: 'reply', id: 'yes', label: 'Yes' }
{ type: 'url', label: 'Open website', url: 'https://openwa.dev' }
{ type: 'call', label: 'Call us', phoneNumber: '+441234567890' }
{ type: 'copy', label: 'Copy code', code: 'WELCOME' }
```

Use reply actions together, or URL/call/copy actions together. Mixing reply and CTA actions is rejected. A URL action can open a map URL; sending a location card is a separate operation. Opening a URL, placing a call or copying text does not produce a promised response event.

Buttons and native messages accept text, image, video or document headers:

```ts
{ type: 'text', text: 'Welcome' }
{ type: 'image', source: 'https://example.com/photo.jpg', title: 'A photo' }
{ type: 'document', source: '/absolute/path/brochure.pdf', filename: 'brochure.pdf' }
```

Media sources can be HTTP(S) URLs, file paths on the open-wa host, or base64 data URLs, and open-wa uploads them before sending. A document saved by a website builder should use URLs or data URLs rather than paths on someone's computer. Test video and document headers with your recipients before relying on them. Bookings have no header.

### Lists

![Illustration of a list message and its sectioned option picker](/images/interactive/sectioned-list.png)

*Group a longer menu into sections and handle the selected row ID.*

```ts
await client.sendInteractive(to, {
  type: 'list', body: 'Choose a service', buttonLabel: 'View services',
  sections: [{ title: 'Help', rows: [
    { id: 'install', title: 'Installation', description: 'Get started' },
    { id: 'account', title: 'Account help' },
  ] }],
});
```

Row IDs must be unique across sections. A selected row arrives as `type: 'list'` with `id` and optional `label`.

### Forms

![Illustration of a form with a single-choice question](/images/interactive/form-single-select.png)

*Ask for one choice with singleSelect.*

![Illustration of a form with several checked options](/images/interactive/form-multi-select.png)

*Collect several selections with multiSelect.*

```ts
const subscription = client.onFormResponse(response => {
  console.log(response.messageId, response.originalMessageId, response.answers);
  // { size: 'small', extras: ['delivery', 'gift'] }
});
await client.sendInteractive(to, {
  type: 'form', title: 'Your preferences', body: 'Tell us what you need',
  questions: [
    { type: 'singleSelect', id: 'size', label: 'Choose a size', options: [
      { id: 'small', label: 'Small' }, { id: 'large', label: 'Large' },
    ] },
    { type: 'multiSelect', id: 'extras', label: 'Choose extras', options: [
      { id: 'delivery', label: 'Delivery' }, { id: 'gift', label: 'Gift wrapping' },
    ] },
  ],
});
// Stop this subscription later:
subscription.off();
```

Question IDs are unique within the form, and option IDs within each question. `allowCustomAnswer` is optional; applications should handle returned values beyond predefined option IDs when enabling it. Selection-count/required-field rules beyond the exposed choices are not implied by labels such as “choose two”.

![Illustration of a completed multi-question form and structured response object](/images/interactive/form-response.png)

*Question IDs connect the choices the recipient sees to the answers your code receives.*

`onFormResponse` filters the same underlying stream as `onInteractiveResponse`; registering both deliberately delivers a form submission to both handlers. Responses carry `messageId`, `chatId`, `senderId`, optional `originalMessageId`/`timestamp`, and `raw`. `originalMessageId` may be a stanza ID rather than a full serialized key. Unexpected native response formats remain available as `type: 'native'` with `name`, `parameters` and an optional `parseError`.

HTTP integrations can subscribe to the same responses before sending a message:

```sh
curl -N -H "X-API-Key: $WA_API_KEY" \
  'http://localhost:8080/api/events?topics=interactive.response'
```

Each `interactive.response` event contains the response at `payload.response`. Use its `type` to select forms, replies or list selections, and its `messageId` to deduplicate events in your integration. The stream doesn't keep events for a client that isn't connected. The same response can arrive more than once, for example after a reconnect, so deduplicate by `messageId` and use `timestamp` to reject stale submissions.

### Carousels

![Illustration of two image cards with distinct reply actions](/images/interactive/image-carousel.png)

*Each card has an image and its own actions.*

```ts
await client.sendInteractive(to, {
  type: 'carousel', body: 'Choose a package', cards: [
    { body: 'Starter', header: { type: 'image', source: starterImage },
      actions: [{ type: 'reply', id: 'starter', label: 'Choose Starter' }] },
    { body: 'Pro', header: { type: 'image', source: proImage },
      actions: [{ type: 'reply', id: 'pro', label: 'Choose Pro' }] },
  ],
});
```

Card images upload with the message. Give reply actions distinct IDs across cards so a response tells you which card was chosen.

### Bookings

![Illustration of a booking card and appointment details](/images/interactive/booking-details.png)

*The recipient app supplies the calendar icon and details layout.*

```ts
await client.sendInteractive(to, {
  type: 'booking', title: 'Consultation', body: 'Your booking details',
  buttonLabel: 'View booking',
  booking: {
    startAt: '2026-10-15T10:00:00+01:00', endAt: '2026-10-15T10:30:00+01:00',
    location: 'London', managementUrl: 'https://example.com/bookings/123',
    description: 'Please arrive five minutes early.',
  },
  actions: [{ type: 'url', label: 'Our website', url: 'https://example.com' }],
});
```

open-wa validates booking dates and converts them to UTC whole seconds so the
recipient's app shows the right date and time. For example, `2026-07-26T14:00:00.000+01:00` becomes
`2026-07-26T13:00:00Z`. This happens automatically in `defineInteractiveMessage`,
the SDK, the Easy API and OpenUI, so don't format dates yourself. Invalid calendar
dates and an `endAt` that isn't after `startAt` at whole-second precision are rejected.

Parsed booking dates have the branded TypeScript type `BookingTimestamp`, so
unchecked strings can't be assigned to `DecodedInteractiveContent`. Use
`normalizeBookingTimestamp(value)` when constructing a typed timestamp yourself.
At least one of `location`, `url` or `phoneNumber` is required.

Optional booking fields include `url`, `phoneNumber`, `email` and `labels` (`language`, `meetingType`, `detailsTitle`, `addToCalendar`, `viewOnMap`, `manageBooking`). The recipient app controls the details UI and icon; custom logos and header images aren't supported.

## Advanced and future payloads

`type: 'native'` takes `{ name, parameters? }` actions and optional message `parameters`. Objects are serialized by the implementation; callers do not need to double-encode JSON. Use it for action types the typed variants don't cover yet, and test each one, because passing validation doesn't mean the recipient's app shows it.

`client.sendRawMessage(to, payload)` sends a WhatsApp protobuf **Message** object you build yourself, as JSON. Its Easy API route is `POST /api/messages/sendRaw` with `{ to, payload }`. Pass the message directly, such as `{ interactiveMessage: ... }`, and encode byte fields as base64. It doesn't upload media referenced inside the payload, and view-once and ephemeral wrappers aren't supported. Unknown fields and payloads WhatsApp can't parse are rejected. Prefer the typed content variants for routine messages.

open-wa doesn't retry a failed send, because an uncertain result may already have reached the recipient. `defineInteractiveMessage` validates a document only; it does not check recipient capability, resolve media or send it.

Validation errors identify the invalid JSON field. Media-loading errors identify the header or carousel card, for example `content.cards[1].header.source`. Send errors carry the failure message, and SDK errors keep the underlying error in `cause`.
