# Configuration and CLI

open-wa takes the same settings everywhere: as an object passed to `create()` in the SDK, or, for the Easy API, from a config file, `WA_*` environment variables and command-line flags. This page shows where each one applies and which wins.

## Common settings

- `sessionId`: names the session and keeps its login separate from other sessions.
- `sessionDataPath`: where the encrypted login file, `<sessionId>.data.json`, is saved. It defaults to the working directory.
- `headless`: run the browser in the background (default) or visibly.
- `useChrome` / `executablePath`: which browser to run.
- `qrTimeout` / `authTimeout`: how long to wait for a QR scan and for login.
- `licenseKey`: unlocks [licensed features](/docs/licensing/pricing).
- `chromiumArgs`: extra browser arguments, such as an outbound proxy; see [use an outbound proxy](/docs/guides/proxying-a-session).
- `linkCode`: log in with a [link code](/docs/sessions/link-code) instead of a QR code.
- `port`, `host`, `apiKey`: where the Easy API listens and the key it requires. The defaults are port `8080` on `localhost`, with no key.

## In the SDK

Pass settings straight to `create()`:

```ts
import { create } from '@open-wa/wa-automate';

const client = await create({
  sessionId: 'sales',
  headless: true,
  qrTimeout: 0,
  authTimeout: 60,
  licenseKey: process.env.WA_LICENSE_KEY,
});
```

`create()` uses only the object you pass. It doesn't read `WA_*` environment variables or look for a config file, so read your environment yourself, as above, or import your config file and pass it in. Projects made with `npm init @open-wa` do exactly that.

## In the Easy API

The Easy API (`npx @open-wa/wa-automate`) combines four sources, later ones winning:

1. schema defaults
2. a config file
3. `WA_*` environment variables
4. command-line flags

Arrays are replaced rather than merged, so a later `plugins` list replaces an earlier one.

### Config files

The CLI looks for a config file in the current directory and uses the first match:

1. the `wa` key in `package.json`
2. `wa.config.js`, `wa.config.cjs`, `wa.config.mjs`
3. `wa.config.ts`, `wa.config.mts`, `wa.config.cts`
4. `wa.config.json`
5. `.warc`, `.warc.json`
6. `cli.config.js`, `cli.config.json`

Use `--config ./path/to/file` to load a specific file. A config file can export an object or a function that returns one, and TypeScript files work directly.

### Environment variables

Every setting can be set with a `WA_` variable: drop the prefix, and the rest is converted from `SNAKE_CASE` to the camelCase setting name, so `WA_SESSION_ID` sets `sessionId`. Values are converted to match the setting:

- `true`, `1`, `yes` and `on` become `true`; `false`, `0`, `no` and `off` become `false`.
- Numeric strings become numbers for numeric settings.
- Values starting with `{` or `[` are parsed as JSON for object and array settings.

| Variable | Setting |
| --- | --- |
| `WA_SESSION_ID` | `sessionId` |
| `WA_PORT` | `port` |
| `WA_HOST` | `host` |
| `WA_API_KEY` | `apiKey` |
| `WA_SESSION_DATA_PATH` | `sessionDataPath` |
| `WA_LICENSE_KEY` | `licenseKey` |
| `WA_LINK_CODE` | `linkCode` |
| `WA_HEADLESS` | `headless` |
| `WA_USE_CHROME` | `useChrome` |
| `WA_QR_TIMEOUT` | `qrTimeout` |
| `WA_AUTH_TIMEOUT` | `authTimeout` |
| `WA_PLUGINS` | `plugins` (JSON array) |
| `WA_PLUGIN_CONFIG` | `pluginConfig` (JSON object) |

A few names don't follow the rule: `WA_DEBUG` sets `devtools`, `WA_BROWSER_WS_ENDPOINT` sets `browserWSEndpoint`, `WA_BYPASS_CSP` sets `bypassCSP`, and `WA_USE_LIGHTPANDA` sets `useLightpanda`. The session encryption key also accepts `OPENWA_SESSION_DATA_ENCRYPTION_KEY` and `OPENWA_SESSION_DATA_ENCRYPTION_KEY_FILE`. Other names, such as `PORT` or `API_KEY`, are ignored; map them in a config file if your platform uses them.

### Command-line flags

| Flag | Setting | Description |
| --- | --- | --- |
| `--session-id sales` | `sessionId` | Names the session. |
| `--port 8080`, `-p` | `port` | Port to listen on. |
| `--host 127.0.0.1`, `-h` | `host` | Address to bind to. |
| `--api-key "key"`, `--key`, `-k` | `apiKey` | Requires an `X-API-Key` header on API requests. Set one before exposing the API beyond your machine. |
| `--license-key "key"`, `-l` | `licenseKey` | License key for licensed features. |
| `--config ./wa.config.ts`, `-c` | — | Loads a specific config file. |
| `--headless`, `--headful` | `headless` | Runs the browser hidden or visible. |
| `--use-chrome`, `--use-chromium`, `--use-lightpanda` | browser | Picks the browser to run. |
| `--qr-timeout 0` | `qrTimeout` | Seconds to wait for a QR scan; `0` waits forever. |
| `--no-dashboard`, `--dashboard-port` | `dashboard`, `dashboardPort` | Turns off the dashboard or moves it. |
| `--no-ezqr` | `ezqr` | Turns off the `/qr` endpoint. |
| `--ephemeral` | `ephemeral` | Has no effect on the login: it is always saved to the session file. |
| `--log-console`, `--log-level`, `--verbose` | logging | Prints browser logs, sets the level, or turns on debug output. |
| `--sandbox-chats`, `--sandbox-isolation` | `sandboxChats` | Isolates code run on behalf of a chat; see below. |
| `--pm2`, `--name` | — | Runs under PM2 with the given process name. |

There's no flag for a link code; set `linkCode` in a config file or `WA_LINK_CODE`, and the code is printed in the terminal.

For example, this command:

```bash
npx @open-wa/wa-automate \
  --session-id sales \
  --api-key "$WA_API_KEY" \
  --license-key "$WA_LICENSE_KEY"
```

is equivalent to this config file:

```ts
export default {
  sessionId: 'sales',
  apiKey: process.env.WA_API_KEY,
  licenseKey: process.env.WA_LICENSE_KEY,
};
```

### Choose a browser

The CLI downloads no browser when it installs. It uses an installed Google Chrome by default, and if none is found it asks which browser to download:

- **Chrome for Testing** works with everything, including video and media.
- **Chromium** may lack some proprietary audio and video codecs.
- **Lightpanda** is light but experimental for WhatsApp, and has no rendering, video or screenshots.

`--use-chrome`, `--use-chromium` and `--use-lightpanda` (or `--lightpanda`) choose directly and download on demand. Downloads are cached per user, and your choice is remembered. A first start with no browser and no terminal to ask in needs one of these flags. Set `browser.download: 'never'` to forbid downloads.

Lightpanda mode downloads Lightpanda 1.0.0 the first time and keeps the `/qr` endpoint and terminal QR working. It's experimental: recovering after a reload, sending reliably and long-running sessions aren't confirmed, and Live Portal and screenshots aren't available.

### Flags that do nothing yet

These older flags are accepted but only print a warning:

| Flag | Instead |
| --- | --- |
| `--webhook`, `-w` | Load `@open-wa/integration-webhook`; see [receive webhooks](/docs/guides/receive-webhooks). |
| `--ready-webhook`, `--stats`, `--generate-api-docs`, `--tunnel` | No replacement yet. API docs are always served at `/api-docs/`. |
| `--chatwoot-url`, `--twilio-webhook`, `--bot-press-url` | Use the [Chatwoot integration](/docs/guides/chatwoot) or another plugin. |

`--mcp` and `--api-host` aren't recognised: enable MCP with `mcp: { enabled: true }` in a config file, and use `--host` for the bind address. The `sessionData`, `sessionDataPath` and `skipSessionSave` settings are deprecated in favour of the browser profile in `userDataDir`.

## Sandboxed chat code

`sandboxChats` isolates code or tools that a chat explicitly asks to run through `executeInChatSandbox`. It doesn't change ordinary message handlers or start a browser per chat. `true` uses the process policy; an object sets the boundary and limits:

```ts
export default defineConfig({
  sandboxChats: {
    isolation: 'container', // worker | process | container
    timeoutMs: 30_000,
    idleTimeoutMs: 300_000,
    memoryMb: 256,
    concurrency: 1,
    filesystem: 'none', // none | read-only | workspace
    network: 'none', // none | allowlist
    networkAllowlist: [],
    env: 'none',
    capabilities: ['sendText'],
  },
});
```

Use `container` for code you don't trust. `process` removes globals, environment and filesystem access and limits time, memory and output, but Node's permission model is a second line of defence rather than a complete boundary. `worker` only protects availability around trusted code. Worker and process policies refuse filesystem, network or environment access, so those need `container`.

## Plugins

`plugins` lists the plugins to load, as npm package names or file paths. Each module must have a default export or a named `plugin` export.

```ts
export default {
  plugins: [
    '@open-wa/integration-webhook',
    '@open-wa/integration-chatwoot',
    './plugins/my-local-plugin',
  ],
};
```

`pluginConfig` holds each plugin's settings, keyed by the plugin's name (`meta.name`), which isn't always the package name. If the plugin defines a config schema, open-wa validates its settings before starting it.

```ts
export default {
  plugins: ['@open-wa/integration-webhook', './plugins/moderation'],
  pluginConfig: {
    webhook: {
      url: 'https://your-app.example/webhooks/open-wa',
      headers: { 'X-Webhook-Secret': process.env.WEBHOOK_SECRET },
    },
    moderation: { apiKey: process.env.MODERATION_API_KEY },
  },
};
```

## Keep secrets out of config

Read `apiKey`, `licenseKey`, webhook secrets and plugin tokens from the environment rather than writing them into files you commit. Keep `.env` in `.gitignore`, use your platform's secret store in production, and don't log whole config objects, because `pluginConfig` often contains tokens. [Configuration secrets](/docs/guides/config-secrets) has worked examples.
