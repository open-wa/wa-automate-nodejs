# Custom code

Use this path when you want to embed `@open-wa/wa-automate` in your own Node.js application instead of running only the Easy API.

<Callout type="info" title="Best fit for custom code">
  Choose this path when your app owns business logic, queues, retries, and
  service boundaries directly, and you want the client surface in-process rather
  than only over HTTP.
</Callout>

## Install

<PackageManagerTabs command="@open-wa/wa-automate" />

If your environment has stricter native-install permissions, only fall back to `--unsafe-perm` when you have confirmed you actually need it.

## Minimal example

```ts
import { create } from '@open-wa/wa-automate';

async function start() {
  const client = await create({
    sessionId: 'my-session',
  });

  client.onMessage(async (message) => {
    if (message.body === 'Hi') {
      await client.sendText(message.from, '👋 Hello!');
    }
  });
}

start().catch(console.error);
```

<Callout type="tip" title="Treat this as the smallest useful starting point">
  The first useful production shape usually adds a real config object, a stable
  session id, explicit browser/runtime settings, and logging or queueing around
  message handlers.
</Callout>

## What `create()` does

`create()` launches the automation runtime, restores or authenticates the session, and returns the client surface you use for listeners and actions.

It is the boundary where configuration, browser launch, authentication state, and runtime listeners all meet.

## Build a real launch config

```ts
const client = await create({
  sessionId: 'sales',
  headless: true,
  useChrome: true,
  qrTimeout: 0,
  authTimeout: 60,
});
```

Use `useChrome` or `executablePath` when browser-specific behavior matters for your flow.

<Steps>
  <Step title="Install and create a client">
    Use the install snippet above, then bootstrap `create()` with a stable
    `sessionId`.
  </Step>
  <Step title="Attach listeners and keep them small">
    Keep `onMessage` handlers focused on orchestration, not all business logic.
    Push heavier work into queues or worker processes.
  </Step>
  <Step title="Harden runtime assumptions before production">
    Lock down Chrome/runtime expectations, session recovery, and logging before
    you ship a long-running bot.
  </Step>
</Steps>

## Browser/runtime notes

- If you are using your own Chrome install, make that explicit instead of depending on auto-discovery.
- On Linux hosts, validate browser dependencies before debugging application logic.
- Keep the browser/runtime assumptions the same between local development and production where possible.

## Next steps

- Move session-specific settings into a real config object.
- Read **[Configuration and CLI](/docs/guides/configuration-and-cli)** for the core options.
- Add `ev` listeners if you need QR, session-data, or lifecycle hooks.
- Externalize heavy work to queues or workers instead of doing everything inside one `onMessage` callback.
- Read **[Error handling](/docs/operations-and-troubleshooting/error-handling)** and **[Best practices](/docs/operations-and-troubleshooting/best-practices)** before shipping a long-running bot.

## Runtime notes

- Prefer explicit Chrome configuration when you rely on browser-specific behavior.
- Keep one primary client per process unless you have a clear multi-session orchestration plan.
- Treat all client methods as async operations and await them consistently.
