# Docker

Use Docker when you need a reproducible container runtime with all required Chromium browser dependencies preinstalled.

## Run the Easy API container

```bash
docker run openwa/wa-automate
```

Pass standard CLI flags directly to the container command.

## Image tags

Docker image tags correspond to published package versions. Pin a specific version for reproducible deployments in staging and production.

Use version 4 tags such as `4.76.0` for the current stable release. Use `latest` only when evaluating the v5 alpha image.

## Version 4 and 5 image tags

```bash
# Version 4 stable
docker run openwa/wa-automate:4.76.0

# Version 5 alpha
docker run openwa/wa-automate:latest
```

## Typical production deployment

A standard production deployment:

- Publishes the API port explicitly.
- Persists session credentials using a volume mount.
- Injects the API key and session identifier at container startup.

```bash
docker run -p 8080:8080 --init \
  -v ./sessions:/sessions \
  -e WA_PORT=8080 \
  -e WA_SESSION_ID=sales \
  -e WA_USER_DATA_DIR=/sessions/sales \
  -e WA_API_KEY="YOUR_SECURE_KEY" \
  openwa/wa-automate
```

## Volume mounts for session persistence

Mount a host directory to preserve authentication credentials across container restarts, and point `WA_USER_DATA_DIR` to the mounted path:

```bash
docker run -p 8080:8080 --init \
  -v ./sessions:/sessions \
  -e WA_SESSION_ID=sales \
  -e WA_USER_DATA_DIR=/sessions/sales \
  openwa/wa-automate
```

The container working directory is `/usr/src/app`. By default, the runtime writes browser profile data to `/usr/src/app/_IGNORE_<sessionId>`. Setting `WA_USER_DATA_DIR=/sessions/<sessionId>` directs the runtime to store profile data in the mounted directory.

Keep the mounted directory secure because it contains active authentication tokens for the WhatsApp account.

## Environment variables

Configure the runtime using environment variables:

```bash
docker run -p 8080:8080 \
  -e WA_PORT=8080 \
  -e WA_API_KEY="YOUR_SECURE_KEY" \
  -e WA_SESSION_ID=sales \
  -e WA_USER_DATA_DIR=/sessions/sales \
  -v ./sessions:/sessions \
  openwa/wa-automate
```

In version 5, prefix configuration variables with `WA_` (for example, `WA_PORT`, `WA_API_KEY`, `WA_SESSION_ID`, and `WA_USER_DATA_DIR`).

You can also pass an environment file:

```bash
docker run -p 8080:8080 --env-file .env openwa/wa-automate
```

## Process reaping with the --init flag

Pass `--init` when executing `docker run`. Chromium launches helper and renderer processes, and an init process reaps zombie child processes when they terminate.

```bash
docker run -p 8080:8080 --init openwa/wa-automate
```

## Browser resource requirements

Headless browsers require sufficient CPU and memory. A single WhatsApp Web session requires approximately **700 MB to 1 GB of RAM**.

If the browser crashes unexpectedly, verify container memory limits and shared memory allocation before modifying application code.

## Run on low-memory hosts

<Callout type="error" title="Never pass --single-process or --no-zygote">
These arguments break Chromium's multi-process execution model and cause WhatsApp Web to fail with `Navigating frame was detached` errors. The runtime removes them from `chromiumArgs` by default.
</Callout>

Recommended configurations for resource-constrained hosts:

- Allocate shared memory using `--shm-size=1gb` (or `shm_size: "1gb"` in Docker Compose) to prevent Chromium `/dev/shm` exhaustion.
- Run with `--init` to reap exited child processes.
- Set container memory limits to at least 1 GB per active session.

## Health checks

Configure a container health check to poll the `/api-docs/` endpoint:

```bash
docker run -p 8080:8080 --init \
  -e WA_PORT=8080 \
  --health-cmd="curl -f http://localhost:8080/api-docs/ || exit 1" \
  --health-interval=30s \
  --health-timeout=10s \
  --health-retries=3 \
  openwa/wa-automate
```

## Docker Compose

Define your container configuration using Docker Compose:

```yaml
services:
  openwa:
    image: openwa/wa-automate:latest
    init: true
    ports:
      - "8080:8080"
    volumes:
      - ./sessions:/sessions
    environment:
      WA_PORT: "8080"
      WA_SESSION_ID: sales
      WA_USER_DATA_DIR: /sessions/sales
      WA_API_KEY: ${WA_API_KEY}
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/api-docs/"]
      interval: 30s
      timeout: 10s
      retries: 3
```

Start the service:

```bash
WA_API_KEY="YOUR_SECURE_KEY" docker compose up
```

## Verify session restarts

To verify that credentials persist across container restarts:

1. Launch the container:

   ```bash
   docker run --name openwa-sales -p 8080:8080 --init \
     -v ./sessions:/sessions \
     -e WA_PORT=8080 \
     -e WA_SESSION_ID=sales \
     -e WA_USER_DATA_DIR=/sessions/sales \
     -e WA_API_KEY="YOUR_SECURE_KEY" \
     openwa/wa-automate
   ```

2. Complete the initial authentication flow.
3. Stop and delete the container:

   ```bash
   docker stop openwa-sales
   docker rm openwa-sales
   ```

4. Restart the container using the same parameters.
5. The runtime should restore the session from `./sessions/sales` without requesting a new QR code scan.

## Manage secrets

Do not hardcode credentials in Dockerfiles. Inject secrets at runtime using environment variables, an external `.env` file, or Docker Secrets:

```yaml
services:
  openwa:
    image: openwa/wa-automate:4.76.0
    secrets:
      - openwa_api_key

secrets:
  openwa_api_key:
    file: ./secrets/openwa_api_key.txt
```

## Production best practices

- Pin explicit Docker image tags instead of using `latest`.
- Publish only necessary ports.
- Mount persistent volume storage for session directories.
- Always use the `--init` flag.
- Enforce API key authentication.

## Use the image as a base image

To build a custom container image containing your application logic:

```dockerfile
FROM openwa/wa-automate
ENTRYPOINT []

WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .

CMD ["node", "dist/index.js"]
```
