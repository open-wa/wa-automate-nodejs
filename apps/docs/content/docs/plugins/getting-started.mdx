# Plugin development quickstart

Plugins execute custom TypeScript or JavaScript logic inside the open-wa Easy API process. A plugin can subscribe to events, call client methods, mount HTTP routes, add web dashboard panels, or register Model Context Protocol (MCP) tools for AI agents.

## Plugin capabilities

A plugin package can:

- Subscribe to WhatsApp events (such as incoming messages and lifecycle updates)
- Invoke client automation methods (such as sending messages and decrypting media)
- Mount custom HTTP routes under `/plugins/<name>/`
- Add UI tabs to the web dashboard
- Expose typed MCP tools to AI assistants

Plugins run **inside the Easy API host process**. They interact with the runtime through a security-filtered event gateway and a transport-agnostic client proxy.

### When to build a plugin

| Use a plugin when... | Use an alternative when... |
| --- | --- |
| Building reusable business extensions | Running in an isolated microservice (use `SocketClient`) |
| Sharing logic across multiple session instances | Managing the browser lifecycle directly (use `createClient`) |
| Adding custom dashboard views or HTTP routes | Needing basic event forwarding (use `@open-wa/integration-webhook`) |
| Exposing specialized MCP tools | Requiring custom browser automation primitives |

## Install the Plugin SDK

Install the SDK in your project workspace:

<PackageManagerTabs command="install @open-wa/plugin-sdk" />

The SDK provides:

- `createPlugin()`: Type-safe plugin factory
- `defineConfig()`: Zod wrapper for validating plugin options
- `z`: Re-exported Zod validation library
- TypeScript definitions for all hook payloads and client interfaces

## Build your first plugin

<Steps>
<Step title="Create the plugin module">

Define the plugin using the `createPlugin()` factory:

```ts
import { createPlugin } from '@open-wa/plugin-sdk';

function parseTextMessage(message: unknown) {
  if (!message || typeof message !== 'object') return null;

  const candidate = message as { body?: unknown; from?: unknown };
  if (typeof candidate.body !== 'string' || typeof candidate.from !== 'string') {
    return null;
  }

  return { body: candidate.body, from: candidate.from };
}

export default createPlugin({
  meta: {
    name: 'greeting-bot',
    version: '1.0.0',
    description: 'Greets new contacts with a welcome message',
  },

  init: async ({ client, logger }) => ({
    'message.received': async ({ message }) => {
      const msg = parseTextMessage(message);

      if (!msg) return;

      if (msg.body === 'Hi') {
        await client.sendText(msg.from, '👋 Welcome! How can I help?');
        logger.info('Sent greeting', { from: msg.from });
      }
    },
  }),
});
```

</Step>
<Step title="Define the configuration schema">

Use `defineConfig()` with Zod to enforce typed configuration:

```ts
import { createPlugin, defineConfig, z } from '@open-wa/plugin-sdk';

function parseTextMessage(message: unknown) {
  if (!message || typeof message !== 'object') return null;

  const candidate = message as { body?: unknown; from?: unknown };
  if (typeof candidate.body !== 'string' || typeof candidate.from !== 'string') {
    return null;
  }

  return { body: candidate.body, from: candidate.from };
}

const configSchema = defineConfig((z) =>
  z.object({
    greeting: z.string().default('👋 Welcome!'),
    triggerWord: z.string().default('Hi'),
  })
);

export default createPlugin({
  meta: { name: 'greeting-bot' },
  configSchema,

  init: async ({ client, logger, config }) => ({
    'message.received': async ({ message }) => {
      const msg = parseTextMessage(message);

      if (!msg) return;

      if (msg.body === config.triggerWord) {
        await client.sendText(msg.from, config.greeting);
        logger.info('Dispatched configured greeting', { to: msg.from });
      }
    },
  }),
});
```

</Step>
<Step title="Register event hooks">

The `init` function returns a record of event handlers:

- `'message.received'`: Dispatched when incoming messages arrive
- `'message.sent'`: Dispatched when the local session sends a message
- `'core.started'`: Dispatched once the session reaches ready state
- `'auth.qr'`: Dispatched when a new QR code is generated
- `'dispose'`: Dispatched during runtime shutdown to clean up resources

For the complete list, see the [Hooks reference](/docs/plugins/hooks-reference).

</Step>
<Step title="Organize project files">

Organize your plugin files alongside your open-wa configuration:

```text
my-openwa-app/
  wa.config.mjs
  plugins/
    greeting-bot.mjs
```

Save your plugin implementation in `plugins/greeting-bot.mjs`.

</Step>
<Step title="Load the plugin in configuration">

In `wa.config.mjs`, reference the plugin file and provide runtime options:

```js
export default {
  sessionId: 'sales',
  plugins: [
    new URL('./plugins/greeting-bot.mjs', import.meta.url).href,
  ],
  pluginConfig: {
    'greeting-bot': {
      greeting: 'Hello! Welcome to our customer support.',
      triggerWord: 'hello',
    },
  },
};
```

Key points:

- The `plugins` array accepts npm package names or file URLs.
- The `pluginConfig` object must be keyed by the plugin's `meta.name` (`'greeting-bot'`).

</Step>
<Step title="Start the runtime and verify">

Start the Easy API server:

```bash
npx @open-wa/wa-automate@alpha --config ./wa.config.mjs --port 8080 --api-key "YOUR_SECURE_KEY"
```

Verify in the logs that the plugin loaded:

```text
plugin_loaded { ref: 'file:///.../plugins/greeting-bot.mjs', name: 'greeting-bot', version: '1.0.0' }
plugin_registered { plugin: 'greeting-bot', version: '1.0.0' }
```

Send the configured trigger word (`hello`) to your connected WhatsApp number to verify that the automated response arrives.

</Step>
</Steps>

## Troubleshooting

### Plugin fails to load

- Ensure the path points to valid JavaScript (`.mjs` or compiled `.js`).
- Verify that the module exports `createPlugin(...)` as default or as a named `plugin` export.
- Check that `meta.name` is defined in your plugin object.
- Confirm `pluginConfig` is keyed by `meta.name`.

### Hook does not execute

- **Sensitive event filtering**: Plugins cannot subscribe to internal system events (such as `launch.*`, `browser.*`, `transport.*`, or `license.*`).
- **Hook spelling**: Verify exact string matching against the [Hooks reference](/docs/plugins/hooks-reference).
- **Registration status**: Confirm the plugin registered successfully in server startup logs.

### Duplicate plugin names

If multiple plugins register with the same `meta.name`, initialization fails with `Plugin "<name>" is already registered`. Ensure every plugin has a unique identifier.

## Plugin architecture

### Security-filtered event gateway

Plugins receive an isolated event emitter:

- **Can** subscribe to public messaging and lifecycle events (`on`, `once`, `off`)
- **Cannot** emit events onto the core bus
- **Cannot** intercept authentication tokens or internal browser state

### Transport-agnostic client proxy

Plugins interact with the `client` proxy object. Calls are routed across the runtime transport boundary without direct DOM access.

### Configuration schema validation

When a plugin defines `configSchema`, the runtime validates `pluginConfig[meta.name]` against the Zod schema before calling `init()`. Invalid options halt plugin initialization and log validation issues.

## Recommended use cases

- **CRM synchronization**: Forward customer messages and updates to external CRM platforms
- **Automated triage**: Perform content moderation, auto-responses, or language translation
- **Custom APIs**: Mount specialized webhooks or REST endpoints under `/plugins/<name>/`
- **Dashboard monitoring**: Render custom operational widgets in the web interface
- **AI tooling**: Register Model Context Protocol (MCP) tools for connected agents
