# Plugin security model

Plugins run inside the open-wa host Node.js process under controlled runtime boundaries. Understanding these security boundaries ensures your plugins operate safely and reliably.

## Security restrictions

### Event emission restrictions

Plugins can only **subscribe** to events. They cannot dispatch synthetic events onto the internal event bus.

```ts
// Restricted: The plugin event emitter does not expose an emit() method
events.emit('custom.event', data); // TypeError: events.emit is not a function
```

### Internal event filtering

The runtime filters out internal and sensitive event namespaces before passing events to plugins:

- `launch.*`: Browser initialization and process spawning events
- `browser.*`: Direct CDP and page lifecycle events
- `transport.*`: Raw socket and RPC transport frames
- `license.*`: Commercial license validation payloads
- Authentication session secrets and pairing tokens

### Browser DOM and CDP boundaries

Plugins interact exclusively through the `client` proxy:

- No direct Chrome DevTools Protocol (CDP) socket access
- No direct arbitrary DOM manipulation in the WhatsApp Web page context
- No direct access to session cookies or browser storage

### File system isolation

Plugins do not receive arbitrary file system write privileges. Confine file storage to application data directories or external object storage.

## Allowed operations

### Public event subscriptions

Plugins can register listeners for public messaging, group, and status events:

```ts
events.on('message.received', (payload) => { ... });
events.once('client.ready', () => { ... });
```

### Method invocation

Plugins invoke WhatsApp automation methods through the `client` proxy:

```ts
await client.sendText('447700900000@c.us', 'Hello');
await client.getHostNumber();
await client.ask('setProfileStatus', ['Available']);
```

### Custom HTTP routes

Plugins can mount Hono sub-applications under `/plugins/<name>/`:

```ts
routes: () => {
  const app = new Hono();
  app.get('/health', (c) => c.json({ ok: true }));
  return app;
};
```

### Model Context Protocol tools

Plugins can register AI tools exposed over MCP:

```ts
tool: {
  lookupCustomer: {
    description: 'Lookup CRM record for a contact',
    args: { customerId: z.string() },
    execute: async (args, ctx) => { ... },
  },
};
```

### Web dashboard pages

Plugins can declare custom tabs for the web interface:

```ts
pages: [{ path: '/', title: 'CRM Overview', icon: 'Database' }];
```

## Configuration validation

### Schema validation workflow

When you define a `configSchema` in your plugin, the host validates the configuration before invoking `init()`:

```ts
export default createPlugin({
  meta: { name: 'crm-sync' },
  configSchema: z.object({
    apiUrl: z.string().url(),
    apiKey: z.string().min(1),
  }),
  init: async ({ config }) => {
    // config is guaranteed to match the schema
  },
});
```

### Validation failures

If configuration validation fails:

- The plugin is not initialized.
- A detailed validation error is logged to the console.
- The host process continues running other plugins.

### Handle optional configuration

Use Zod defaults and optional fields to provide sensible fallbacks:

```ts
const configSchema = z.object({
  apiUrl: z.string().url().default('https://api.example.com'),
  apiKey: z.string().optional(),
  retries: z.number().int().positive().default(3),
});

init: async ({ config, logger }) => {
  if (!config.apiKey) {
    logger.warn('No API key configured; read-only mode enabled');
  }
};
```

## Secret management

### Environment variables

Reference environment variables in `wa.config.mjs`:

```js
// wa.config.mjs
export default {
  pluginConfig: {
    'crm-sync': {
      apiKey: process.env.CRM_API_KEY,
    },
  },
};
```

### Environment file support

Store secrets in a local `.env` file added to `.gitignore`:

```bash
CRM_API_KEY="sk_live_secret_key"
```

### Log redaction and sensitive data

Plugin configuration is not logged automatically. However, avoid logging raw configuration objects:

```ts
// Avoid: Emits sensitive API keys to log streams
logger.info('Config loaded', { config });

// Recommended: Log only safe properties
logger.info('Config loaded', { apiUrl: config.apiUrl, hasKey: Boolean(config.apiKey) });
```

### Enforce required API keys

Enforce required keys using Zod validation rules:

```ts
const configSchema = z.object({
  apiKey: z.string().min(1, 'CRM API key is required'),
});
```

### Key rotation

To rotate API keys:

1. Update the secret in your environment or secrets manager.
2. Restart the open-wa session process.
3. The plugin reloads with the updated key during initialization.

## Error handling patterns

### Upstream API failures

```ts
init: async ({ logger }) => ({
  'message.received': async ({ message }) => {
    try {
      const result = await fetchExternalAPI(message);
    } catch (error) {
      const status = (error as { status?: number }).status;
      const messageText = (error as Error).message ?? 'Unknown error';
      if (status === 429) {
        logger.warn('Upstream rate limit reached');
      } else if (status === 401) {
        logger.error('Upstream authentication failed: Invalid API key');
      } else {
        logger.error('API request failed', { error: messageText });
      }
    }
  },
}),
```

### Network connection errors

```ts
try {
  const response = await fetch(url, { signal: AbortSignal.timeout(10000) });
} catch (error) {
  if (error instanceof Error && error.name === 'TimeoutError') {
    logger.warn('Upstream request timed out after 10 seconds');
  } else if ((error as { code?: string }).code === 'ECONNREFUSED') {
    logger.error('Connection refused by upstream host');
  }
}
```

### Validate message payloads

Validate payloads before accessing nested properties:

```ts
init: async ({ logger }) => ({
  'message.received': async ({ message }) => {
    const msg = message as { body?: string; from?: string };
    if (!msg.body || !msg.from) {
      logger.debug('Skipping message without body or sender');
      return;
    }
    // Process validated message
  },
}),
```

### Session connection disconnects

Listen for lifecycle hooks to track session health:

```ts
init: async ({ logger }) => ({
  'core.stopping': async ({ reason }) => {
    logger.info('Session stopping; flushing queues', { reason });
  },

  'client.ready': async ({ sessionId }) => {
    logger.info('Session reconnected', { sessionId });
  },
}),
```

### Error escalation strategies

- **Log and continue**: For transient network errors or bad request formats. The plugin continues processing subsequent messages.
- **Throw**: For invalid runtime configurations or critical missing dependencies.
- **Clean up with `dispose`**: Terminate timers, close database pools, and flush remaining queues during shutdown.
