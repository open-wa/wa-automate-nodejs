# How it works

open-wa links a normal WhatsApp account as a linked device and runs it in a
browser that open-wa controls. Whatever you build talks to the one process that
owns that browser. This page explains that process, how a session becomes ready
and where the login is kept, so you can choose between the SDK, Easy API and
SocketClient.

## One process owns the session

```text
WhatsApp account (linked device)
        |
        v
open-wa session  ── runs in one Node.js process with its browser
        |
        +──> SDK: your code calls create() in the same process
        |
        +──> Easy API: HTTP routes, the event stream, webhooks, MCP
                 |
                 +──> SocketClient, Cloudflare session proxy, your services
```

The process that starts the browser owns the session. The SDK runs in that
process. Easy API runs it as a server, and everything else, such as
SocketClient, MCP clients or your Python app, sends commands to that server
instead of owning a browser of its own.

| Mode | Use it when |
| --- | --- |
| **SDK** | Your application is in Node.js and should handle messages in-process. Start with [`create()`](/docs/getting-started/custom-code). |
| **Easy API** | Your application is in another language, runs elsewhere, or you want the Neo dashboard. Start with [Easy API](/docs/getting-started/easy-api). |
| **SocketClient** | A Node.js service needs SDK-style methods and listeners against a running Easy API. See [SocketClient](/docs/guides/socket-client). |

## Lifecycle

A session moves through these states, which `client.getState()` reports:

1. **`STARTING`**: open-wa resolves its configuration, opens the browser and
   loads WhatsApp.
2. **`AUTHENTICATING`**: the account isn't linked yet, so a QR code or
   [link code](/docs/sessions/link-code) is waiting, or a saved login is being
   restored.
3. **`READY`**: the session can send and receive. `create()` resolves here, and
   Easy API starts accepting method calls.
4. **`DISCONNECTED`**: the connection dropped. [Detect logouts](/docs/sessions/detect-logouts)
   shows how to react.
5. **`STOPPED`**: `stop()` ran and the browser has closed.

Easy API reports the same thing at `/health`: wait for `connected: true` and
`session.ready: true` before you send. A license problem doesn't stop a session
from becoming ready; it only leaves licensed features locked. See
[Sessions and login](/docs/sessions) for pairing, events and recovery.

## Where the login is saved

After you link the account, open-wa saves the login in an encrypted file named
after the session, `<sessionId>.data.json`. By default it's in the working
directory; set `sessionDataPath` to a folder or a full file path to move it.
On the next start with the same `sessionId`, open-wa restores the login from
that file without a QR code.

The browser profile itself is temporary and is rebuilt on each start, so
`userDataDir` and `ephemeral` don't affect whether the login is kept. Back up
the session file, not the profile, and treat it as a password. Set
`sessionDataEncryptionKey` or `sessionDataEncryptionKeyFile` to use your own
encryption key, and set `s3Sync` when the file must live outside the machine.

The CLI also writes a small `.open-wa/` cache with the browser it chose. That's
a convenience, not login data.

## Where plugins fit

Plugins run inside the process that owns the session. They receive public
events, such as messages, acks, group and call events, and they can add HTTP
routes, dashboard pages and AI tools.

```text
session events ──> plugin hooks ──> your services
                    plugin routes, dashboard pages, tools
```

A plugin can't subscribe to login data such as QR codes or link codes, or to
open-wa's internal startup, license and delivery events, and it can't emit
events of its own onto the session. The [plugin security model](/docs/plugins/security-model)
has the details.
