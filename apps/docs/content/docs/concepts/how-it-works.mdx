# How it works

This guide explains how open-wa manages browser processes, injects runtime bridges, and exposes client surfaces to your application.

## Mental model

The open-wa architecture operates across four distinct stages:

<Steps>
<Step title="Launch WhatsApp Web">
    A headless or visible browser process loads the WhatsApp Web client.
</Step>
<Step title="Inject the runtime bridge">
    open-wa injects automation scripts and state observers into the page context.
</Step>
<Step title="Expose the client interface">
    The Node.js runtime provides an API for actions, event listeners, and lifecycle hooks.
</Step>
<Step title="Connect your application">
    Your application interacts with the client directly, through Easy API HTTP endpoints, or via `SocketClient`.
</Step>
</Steps>

## Runtime architecture

The following diagram illustrates how different integration surfaces reach the underlying browser session:

```text
Browser session
  WhatsApp Web
    |
    v
Runtime bridge injected by open-wa
    |
    v
Client surface
  actions, listeners, lifecycle, events
    |
    +--> Library mode
    |      Node.js application invokes createClient()
    |
    +--> Easy API
    |      HTTP endpoints, OpenAPI documentation, webhooks, MCP server
    |
    +--> Remote consumers
           SocketClient, Cloudflare proxy, third-party services
```

The browser page remains the authoritative source of truth. The outer layers define how your application code interacts with that session.

## Browser injection

open-wa connects to a browser page, navigates to WhatsApp Web, and injects runtime bridge code into the JavaScript execution context. This bridge allows Node.js to invoke WhatsApp Web functions and subscribe to real-time events.

Bridge verification is a mandatory part of session initialization. The runtime confirms that the internal store and method interfaces are accessible before marking the client as ready. If a page navigation or reload detaches the bridge, open-wa detects the disconnect and reinjects the bridge automatically.

## API, SocketClient, and MCP architecture

All external surfaces build on the core client interface:

- **Easy API**: Receives HTTP requests, validates session readiness, and executes the requested client methods.
- **SocketClient**: Connects to an external Easy API daemon over HTTP RPC and Server-Sent Events (SSE).
- **MCP server**: Exposes client methods as tools using the Model Context Protocol. Tool execution is paused until the underlying session connects.

Remote consumers never manage the browser process directly; they communicate with the server process hosting the session.

## Lifecycle states

A session progresses through these operational states:

1. **starting**: The runtime parses configuration, launches the browser process, and navigates to the page.
2. **QR**: The browser requires authentication; a terminal QR code or link code is generated.
3. **authenticated**: WhatsApp Web verifies credentials; the runtime injects the bridge and synchronizes state.
4. **ready**: The bridge is verified and client methods can execute.
5. **stopping**: The shutdown sequence drains event listeners, flushes queues, and terminates plugin processes.
6. **stopped**: Browser processes and temporary resources are released.

In code, lifecycle events use constants such as `STARTING`, `AUTHENTICATING`, `READY`, and `STOPPED`.

## Session data storage

Session credentials are saved in the browser profile directory. Unless you enable `ephemeral` mode, open-wa creates a persistent `userDataDir` on disk. If you omit an explicit path, the runtime derives the folder name from the session ID (for example, `./_IGNORE_<sessionId>`).

This profile stores indexed databases, local storage, and cookies so that subsequent process launches resume without re-authenticating.

## Plugin architecture

Plugins intercept events and register custom routes or tools:

```text
Runtime events
  |
  v
HyperEmitter
  |
  v
PluginHost
  |
  +--> Plugin hooks
  +--> Plugin HTTP routes
  +--> Plugin dashboard pages
  +--> Plugin MCP tools
  |
  v
External services
  Webhooks, Chatwoot, S3, custom APIs
```

## Security-filtered event pipeline

Plugins do not access the raw internal event emitter. `PluginHost` provides an isolated event gateway for each plugin that allows subscriptions only to public, non-sensitive events.

Internal startup, patching, persistence, license, and authentication payloads (such as QR codes and pairing secrets) are filtered from plugin event streams.

Plugins cannot call `emit()` directly; they consume events and provide handler hooks.

## Primary usage modes

<Tabs items={['Library mode', 'Easy API mode', 'Remote consumer mode']}>
<Tab value="Library mode">
    Invoke `createClient()` directly to embed browser management within your Node.js application.
</Tab>
<Tab value="Easy API mode">
    Run the Easy API daemon to expose HTTP endpoints, generated documentation, and MCP tools.
</Tab>
<Tab value="Remote consumer mode">
    Connect to a running Easy API daemon using `SocketClient` to separate application logic from browser compute overhead.
</Tab>
</Tabs>
