# Pricing and licensing

Use this page to decide whether your workflow needs a runtime license and where
to review the current open-wa onboarding offer.

If you already know the gated method or runtime behavior you need, read
**[Licensed features](/docs/licensing/licensed-features)** for the operational
details before you buy.

<Callout type="note" title="Prices live in the purchase flow">
  Prices and terms are shown in the first-party account flow and can change.
  It currently opens the “Open-WA License” onboarding offer; review the current offer and
  terms there before deciding what to purchase.
</Callout>

## First decision: do you need a key?

Start from the behavior your workflow needs. Method metadata marks methods as
`restricted`, `insiders`, or `none`; runtime-specific checks can add a
requirement to a particular path, and neither metadata nor a license makes an
unsupported method available in your deployed version.

<Callout type="tip" title="Buy for the runtime you will operate">
  A license is part of the runtime launch path. Validate it with the host
  account, session, deployment clock, and exact gated method you plan to use in

## What a license key changes at runtime

<Steps>
  <Step title="You provide the key at launch">
    Supply the key through runtime config or the Easy API / CLI `--license-key`
    option.
  </Step>
  <Step title="The runtime checks the key">
    When the host account context is available, the runtime sends the key to the
    validation service. It classifies the result before it marks the client
    ready.
  </Step>
  <Step title="The gated method still needs testing">
    A valid key is not a substitute for testing. Confirm the exact restricted or
    insiders method works in the same session and deployment you plan to run.
  </Step>
</Steps>

## Integration buyers

Integrations do not need a separate license just because they are integrations.
The license decision follows the behavior the integration calls.

## Team and organization buying

For team or organization questions, review the current offer in the first-party
account flow and use the project support paths for terms it does not explain.
The docs do not define
multi-seat terms, per-developer scope, customer deployment scope, transfer rules,
or support service levels.

If the purchase has multiple users, accounts, environments, or customer deployments,
do not assume its scope. If the current offer does not answer your purchase
question, use Discord or the paid support links in the project README.
