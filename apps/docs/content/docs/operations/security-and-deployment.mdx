# Security and deployment

Anyone who can reach the Easy API can use the WhatsApp account behind it, so production deployments need an API key, a private network or HTTPS in front, and a protected session file. The Easy API listens on `localhost:8080` by default, which keeps it off the network until you choose otherwise with `--host` or `WA_HOST`.

## API keys

### Set a key

Without a key, every API route is open to anyone who can reach the port. Generate a random key:

```bash
openssl rand -hex 32
# or
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Supply it through the environment rather than a committed file:

```bash
export WA_API_KEY="your-generated-key"
npx @open-wa/wa-automate
```

The Easy API reads `WA_API_KEY` on its own; `--api-key` works too. Clients then send it in the `X-API-Key` header. In production, keep it in a secrets manager such as AWS Secrets Manager, HashiCorp Vault or Doppler.

### Rotate a key

The key is read at startup, so rotating it means restarting with the new value. Keep the session file; a new key doesn't require linking WhatsApp again.

### If a key leaks

1. Stop the running session.
2. Generate a new key and restart with it.
3. Review what was done with the old key.
4. If you suspect someone used the account, log out the linked device from your phone and link it again.

## Network

### Don't expose the port directly

Never put the Easy API on the internet without a key. `/health` stays public even with a key set, and it can include the QR code and diagnostics, so keep it off any public route. At a minimum, set an API key, put HTTPS in front with a reverse proxy, and restrict access to known IP addresses where you can.

### Reverse proxy

**nginx:**

```nginx
server {
    listen 443 ssl;
    server_name whatsapp-api.example.com;

    location /health { return 404; }

    location / {
        proxy_pass http://localhost:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

**Caddy:**

```
whatsapp-api.example.com {
    respond /health 404
    reverse_proxy localhost:8080
}
```

The Easy API rate-limits each client to 100 requests a minute, keyed on `X-Forwarded-For` or `X-Real-IP`, so make sure your proxy sets one of them.

### Cloudflare Tunnel

Cloudflare Tunnel reaches a local API without opening an inbound port:

```bash
cloudflared tunnel --url http://localhost:8080
```

That still creates a public route, so keep the API key on and block `/health`. For remote access without any public route, use the [Cloudflare session proxy](/docs/guides/cf-proxy).

### Firewall

If you must expose the port, allow only the addresses that need it:

```bash
ufw allow from 1.2.3.4 to any port 8080
```

## Webhooks

When open-wa sends webhooks to your service, use an HTTPS URL, add a shared-secret header through the webhook plugin's `headers` setting, and reject requests without it. The plugin doesn't sign payloads. Size your receiver for the plugin's defaults: 10 concurrent deliveries, 3 retries with exponential backoff from 1 second, and a 30-second timeout. See [receive webhooks](/docs/guides/receive-webhooks).

## MCP

MCP needs an API key and won't start without one. Each MCP request must send the key in the `X-API-Key` header (`api_key` and `key` headers also work); query-string keys aren't accepted.

MCP exposes every Easy API method as a tool, with no per-tool permissions, so any agent holding the key can read every chat, message any contact and see session details. Keep the key secret, don't give it to agents you don't trust, and keep the endpoint behind your reverse proxy. Watch usage in your proxy's access logs and on the dashboard's MCP page.

## Cloudflare session proxy tokens

The [Cloudflare session proxy](/docs/guides/cf-proxy) authenticates consumers with tokens. Rotate them periodically: update the token in the Worker, update the consumer's connection string, and test the new connection before removing the old token.

## Deployment layouts

### Single server

```
[Your app] ←→ [open-wa Easy API] ←→ WhatsApp
```

Run `npx @open-wa/wa-automate` with `WA_API_KEY` set, under PM2, systemd or another process manager.

### Docker

Follow the [Docker guide](/docs/getting-started/docker): it persists the session file, sets the key and keeps the port bound to loopback, because `/health` is public.

### Cloudflare proxy and a local session

```
[Your app] ←→ [Cloudflare session proxy] ←→ [open-wa Easy API, local] ←→ WhatsApp
```

No inbound ports are open on your server. See the [Cloudflare session proxy](/docs/guides/cf-proxy).

### Kubernetes

Run one pod per session, since sessions share no state, and give each a persistent volume for its session file. Scale by adding sessions rather than replicas of one session, because two processes must never share a profile.
