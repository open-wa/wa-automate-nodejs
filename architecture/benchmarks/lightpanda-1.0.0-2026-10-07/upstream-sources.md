## Remaining differences visible in the exact source baseline

### CryptoKey structured cloning is still absent upstream

The [`Value.zig` host clone list](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/js/Value.zig#L467-L480) includes Blob/File/FileList/ImageData/DOM geometry types and omits CryptoKey. The [`CryptoKey` JS metadata](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/webapi/CryptoKey.zig#L233-L247) exposes accessors but has no structured serialization hooks. Thus the merge of general structured-clone or WebCrypto support does not close this gap. A custom native CryptoKey clone implementation must remain identified as an OpenWA-local change until upstream accepts an equivalent implementation.

Targeted GitHub issue/PR searches for CryptoKey found #2666, and searches for structuredClone found #1790/#2858/#2771, but **no exact public issue/PR for CryptoKey structured-clone support was located**. This is a search result, not a claim that no relevant discussion exists anywhere.

### Clone support is not MessagePort/ArrayBuffer transfer support

[`Value.zig` explicitly documents unsupported transferables](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/js/Value.zig#L383-L395). [`MessagePort.postMessage`](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/webapi/MessagePort.zig#L70-L99) takes only the message and uses a structured clone. [`Worker.postMessage`](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/webapi/Worker.zig#L338-L354) likewise takes only data, as does [`DedicatedWorkerGlobalScope.postMessage`](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/webapi/DedicatedWorkerGlobalScope.zig#L78-L80). Those signatures and the serializer path do not provide transfer-list ownership semantics. An ArrayBuffer's being cloneable as a built-in does not implement detachment and transfer, and a MessagePort's being present does not implement moving its endpoint to another realm.

No exact public transferables implementation PR was located by the targeted `transferable`/MessagePort/ArrayBuffer searches. #2771 is a real merged cloning improvement but must not be described as transfer-list support.

### Named-worker support remains a separate option

[`WorkerOptions`](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/webapi/Worker.zig#L67-L88) has only a `type` field; it has no `name`. [`DedicatedWorkerGlobalScope`'s exported API](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/webapi/DedicatedWorkerGlobalScope.zig#L239-L253) likewise has no name accessor. Worker API presence and worker-name propagation cannot be treated as interchangeable. No exact public named-worker fix was located by the targeted search.

### IndexedDB request lifetimes require more than transaction ownership

[`IDBRequest.acquireRef/releaseRef`](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/webapi/storage/idb/IDBRequest.zig#L90-L142) forwards transaction-owned wrapper pins to the transaction. [`IDBTransaction.newRequest/enqueue`](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/webapi/storage/idb/IDBTransaction.zig#L504-L513) stores raw request pointers in the native queue. These mechanisms preserve transaction arena lifetime but do not by themselves demonstrate that the JavaScript request wrapper and JavaScript-side metadata remain alive while a request is pending. This source distinction is relevant to the custom pending-wrapper retention change; it is **not** a claim that this alone proves the exact cause of every observed Dexie failure.

The linked upgrade-event and OpenContext fixes are related lifetime work with different ownership targets. An exact upstream issue/PR matching pending IndexedDB request-wrapper retention was not located by the targeted IDBRequest/IndexedDB searches.

### DOMStringList iterator has a concrete ownership discrepancy

The [`DOMStringList` list destructor](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/webapi/collections/DOMStringList.zig#L45-L58) releases `_arena`. Its [`keys/values/entries` methods and iterator](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/webapi/collections/DOMStringList.zig#L81-L109) pass the `_items` slice to an iterator without retaining the list. The nearby comment claims the slice is page-arena backed, but the actual list owns a released arena. **Inference from source:** an iterator can outlive the owning list wrapper and access a slice whose backing arena was released. The custom iterator lifetime fix addresses this ownership relationship. The OpenWA run's crash evidence is separate from this upstream-source finding.

No exact public DOMStringList issue/PR was located. General iterator fixes such as [#3817, pass default params to iterator](https://github.com/lightpanda-io/browser/pull/3817), and [#3198, webapi: Give iterator to types with an indexed property](https://github.com/lightpanda-io/browser/pull/3198), are not evidence that this list ownership discrepancy is resolved.

### Experimental Service Workers and CacheStorage are not a current single-cause diagnosis

[`Config.ExperimentalFeatures`](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/Config.zig#L241-L244) defaults Service Workers off. [`Env.zig`](https://github.com/lightpanda-io/browser/blob/e98a770e0ef37083b64e40d6047ab5fa5893cbff/src/browser/js/Env.zig#L341-L343) hides their API when that flag is disabled. #3512 implemented a shell and #3562 added in-memory caching. These are real upstream changes, but neither linked PR is a claim of complete lifecycle, fetching and persistence parity. A local choice to expose CacheStorage while keeping incomplete Service Workers disabled must be documented as a custom choice rather than an official upstream supported configuration.

Authenticated library READY/read-only success in a custom run, if backed by the run owner's evidence, would disprove an absolute claim that merely lacking full Service Workers makes pairing or all authenticated work impossible. It would still leave actual database, worker, recovery, outbound and frontend correctness to establish separately.

## Why merged/closed issues can coexist with our failures

1. **Status is narrower than semantics.** #2732's original missing `indexedDB` global is addressed; that does not address every CryptoKey serialization, transaction, request-wrapper or iterator lifetime requirement in a complex client. #2771 clones values; it does not transfer their ownership.
2. **Stable, rolling nightly and main are different revisions.** Compression Streams, DOMException/CDP descriptions and failed-root-navigation handling merged after stable 1.0.0. #3843 merged after the latest successful nightly run. Cache labels and the unchanged nightly tag do not identify the actually executing binary.
3. **A merged native fix does not repair adapter logic.** Host commit ordering, runtime readiness predicates, module mapping/aliases, checkpoint scheduling and dashboard connection management are OpenWA concerns whose correctness is not implied by upstream issue closure.
4. **Feature presence does not prove full application behavior.** A socket, QR, phone-linked device, successful snapshot, readable chats and delivered outgoing messages are distinct milestones. A public report should state which milestone was actually established, which subsequently regressed and which remains unverified.

## Source-reading limits and recommended public wording

- The GitHub and source reads in this task did not run the application, execute native binaries, build packages, add tests, inspect private data or attempt outbound delivery.
- The custom build name `1.1.0-dev+openwa.native.8` and its modification list come from the supplied experiment context; upstream sources cannot verify the exact local binary content. Report the executable identity/hash from the experiment owner's non-sensitive provenance, if available.
- Say **“related merged fix”**, **“remaining source gap”** or **“unresolved hypothesis”** precisely. Do not call all observed failures upstream defects, do not claim a closed issue fixes a different lifecycle problem, and do not claim a resource benchmark establishes usable WhatsApp session parity.
- Public issue references should contain source/PR links and scrubbed status/error-code summaries. Do not attach raw CDP/browser logs or screenshots of a real account, since they can contain identifiers, authentication material or message data even when the selected error appears harmless.
